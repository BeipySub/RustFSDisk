## 2. 总体技术架构

系统采用“双后端 + 双前端 + 双数据库 + 运输盘离线协议”的架构。

```text
边缘端前端
  <-> 边缘端后端
      <-> 边缘端本地数据库
      <-> 边缘 RustFS S3 API
      <-> Linux udev / mount / filesystem
      <-> 运输硬盘

运输硬盘
  -> /rustfs-transfer/disk_info.json
  -> /rustfs-transfer/manifests/export_manifest.json
  -> /rustfs-transfer/manifests/export_manifest.sha256
  -> /rustfs-transfer/data/ 密文对象或密文分块
  -> /rustfs-transfer/meta/ 对象元数据
  -> /rustfs-transfer/logs/ 导出导入日志
  -> /rustfs-transfer/quarantine/partial/ 未完成临时文件隔离区

中控端前端
  <-> 中控端后端
      <-> 中控端数据库
      <-> 中控 RustFS S3 API
      <-> Linux udev / mount / filesystem
      <-> 运输硬盘

边缘端后端
  -> 通过 HTTP API 向中控端校验身份、硬盘和领取数据加密密钥
```

核心边界：

- 边缘端和中控端不通过 WebSocket 互相传输业务数据。
- WebSocket 只用于后端向本端前端推送实时状态。
- 运输盘是离线数据交接载体。
- 中控端数据库是运输盘注册、边缘站点、密钥、导入账本的权威库。
- 边缘端数据库只保存本地扫描、导出任务和运行状态。

## 3. 后端技术选型

### 3.1 后端语言

推荐：Rust。

原因：

- 适合大文件流式读写、加密、校验和高并发 I/O。
- 适合 Linux 后台服务和 systemd 部署。
- 对内存占用、错误处理和长期运行稳定性更可控。

### 3.2 HTTP 和 WebSocket 服务

推荐：

- HTTP API：Rust Web 框架，建议使用轻量异步框架。
- WebSocket：与 HTTP 服务同进程提供，按事件结构推送前端状态。
- 异步运行时：Tokio。

职责：

- 中控端后端提供边缘端鉴权、硬盘校验、密钥领取、对象导入、WebSocket 推送。
- 边缘端后端提供本地硬盘识别、RustFS 扫描、导出任务、WebSocket 推送。

### 3.3 S3 访问

推荐：

- 使用 S3 兼容 SDK 访问 RustFS。
- 边缘端只使用 `List`、`HEAD`、`GET`。
- 中控端使用 `HEAD`、`PUT`，必要时创建归档 bucket。

边缘端禁止：

- 删除源对象。
- 修改源对象。
- 修改源对象 metadata。

### 3.4 数据库访问

推荐：`sqlx` 或同类显式 SQL 方案。

原因：

- 本项目表结构和状态机强依赖 SQL 约束。
- 显式 SQL 更容易审查唯一键、事务、状态更新和幂等逻辑。
- 迁移脚本可直接对应 [数据库设计.md](数据库设计.md)。

## 4. 数据库技术选型

### 4.1 中控端数据库

推荐：PostgreSQL。

用途：

- 运输盘注册。
- 边缘站点注册和鉴权信息。
- 数据加密密钥记录。
- 导入任务。
- 全局对象导入账本。

原因：

- 中控端是权威端，需要更可靠的事务、唯一约束和并发能力。
- `object_ledger` 可能持续增长，PostgreSQL 更适合长期审计和查询。

### 4.2 边缘端数据库

推荐：PostgreSQL。

用途：

- RustFS 对象扫描快照。
- 导出任务。
- 导出对象状态。
- 运输盘运行状态。

原因：

- 中控端和边缘端统一数据库技术栈，降低 SQL 方言、迁移脚本和开发调试差异。
- 边缘端也需要较多任务状态、对象快照和分块记录，PostgreSQL 的事务、索引和并发能力更稳。
- 现场如果已经具备 PostgreSQL 部署和运维能力，统一 PostgreSQL 比混用 SQLite 更容易长期维护。
- 边缘端 PostgreSQL 仍只作为本地运行账本，不作为中控端权威库。

### 4.3 时间格式

所有数据库 `timestamp` 字段统一保存 UTC 时间。

推荐格式：

```text
2026-08-08T06:30:00Z
```

前端展示时再转换为本地时间。

## 5. 前端技术选型

推荐：

- Vue 3
- TypeScript
- Vite
- Pinia 或轻量状态管理
- WebSocket 客户端

原因：

- 当前页面以状态展示、任务列表、进度、异常提示为主，Vue 适合快速构建运维型界面。
- 中控端前端和边缘端前端独立部署，但可复用组件和事件类型定义。

前端重点：

- 不直接轮询数据库。
- 实时状态通过 WebSocket 展示。
- 页面刷新后通过 HTTP 查询任务汇总状态。
- 多盘并行展示必须以 `disks[]` 为每块盘的独立进度来源。

## 6. Linux 系统能力选型

### 6.1 热插拔识别

推荐：

- Linux udev 监听硬盘 add/remove/change 事件。
- 程序启动时扫描当前已存在硬盘。

识别信息：

- 设备路径。
- 挂载路径。
- 文件系统。
- 容量。
- 剩余空间。
- SN。
- 盘内 `disk_info.json`。

### 6.2 文件系统和挂载

推荐：

- 运输盘文件系统固定为 ext4。
- 中控端负责初始化和重新初始化运输盘。
- 边缘端不得自动清盘。

写盘要求：

- 临时文件使用 `.partial`。
- 写完后 fsync。
- 校验成功后原子重命名。
- `disk_info.json` 和 manifest 写入也必须使用临时文件 + fsync + 原子重命名。

## 7. 加密技术选型

推荐：AES-256-GCM。

职责：

- 中控端生成和保存 `disk_data_key`。
- 边缘端通过 `/api/disk/export-key` 领取本次运输盘生命周期内的数据加密密钥；密钥不按时间过期，导入完成并重新初始化后旧密钥退役。
- 运输盘只保存 `data_key_id`、nonce、tag、密文大小、密文 SHA256 等非敏感信息。
- 运输盘不得保存明文密钥。

校验边界：

- `ciphertext_sha256`：校验运输盘密文文件是否损坏。
- `tag`：校验密文是否被篡改。
- `plaintext_sha256`：校验解密后的对象内容是否与源对象一致。

## 8. 并发和任务模型

### 8.1 边缘端导出

推荐模型：

```text
Scanner
  -> 扫描 RustFS 对象
  -> 写 local_object_snapshot

Planner
  -> 判断对象稳定性
  -> 计算运输盘 object_budget_bytes
  -> 分配对象或分块
  -> 写 export_object

DiskWorker
  -> 每块运输盘一个 worker
  -> 流式读取 RustFS
  -> AES-256-GCM 加密写 .partial
  -> 更新内存 ProgressAggregator
  -> 校验、重命名、写 meta 和 manifest

WebSocket Publisher
  -> 读取内存 ProgressAggregator 快照
  -> 推送前端
```

导出运行中进度边界：

- `COPYING` 阶段的当前对象进度、分盘进度、全局进度、速度和剩余字节数由 DiskWorker 在内存 `ProgressAggregator` 中实时维护。
- WebSocket Publisher 每 1 秒读取内存快照推送前端。
- PostgreSQL 只保存对象状态变更、任务阶段、错误码、分配锁、nonce 唯一记录、低频 checkpoint 和最终结果。

### 8.2 中控端导入

推荐模型：

```text
DiskDetector
  -> 识别 SEALED 运输盘

ImportWorker
  -> 每块 SEALED 运输盘一个 worker
  -> 校验 disk_info.json 和 manifest
  -> 校验 ciphertext_sha256
  -> 解密并校验 plaintext_sha256
  -> 上传中控 RustFS
  -> 更新内存 ProgressAggregator
  -> 写 object_ledger
  -> 低频更新 import_job

WebSocket Publisher
  -> 读取内存 ProgressAggregator 快照
  -> 推送前端
```

导入运行中进度边界：

- `IMPORTING` 阶段的当前对象进度、速度、已导入字节数和剩余字节数由 ImportWorker 在内存 `ProgressAggregator` 中实时维护。
- WebSocket Publisher 每 1 秒读取内存快照推送前端。
- `object_ledger` 成功对象立即写入，`import_job` 只低频更新汇总字段和任务最终结果。

## 11. 第一版实现优先级

第一优先级：

- 中控端运输盘注册和初始化。
- 边缘端硬盘识别和中控校验。
- 边缘端 RustFS 扫描和稳定性判断。
- 单盘或多盘普通对象导出。
- AES-256-GCM 加密落盘。
- 中控端导入、解密、上传和写账本。
- WebSocket 实时进度。

第二优先级：

- 跨盘超大对象分块。
- 导入失败恢复增强。
- 小文件极多场景下的性能优化。
- object_ledger 批量写入优化。

## 12. 当前仍需开发时细化的内容

以下内容不阻塞第一版开工，但建议按下列默认选择进入开发，避免实现阶段反复摇摆。

### 12.1 Rust crate 选择

第一版推荐使用稳定主流 crate，版本在 `Cargo.lock` 中锁定，后续升级必须单独验证导出、导入、加密和数据库迁移流程。

后端核心推荐：

- 异步运行时：`tokio`。
- HTTP/WebSocket：`axum`，同进程提供 HTTP API 和 WebSocket。
- 数据库访问：`sqlx`，启用 PostgreSQL、runtime tokio、TLS 和 chrono/uuid/json 支持。
- S3 访问：`aws-sdk-s3`，按 S3 兼容 endpoint 访问 RustFS。
- 序列化：`serde`、`serde_json`。
- 配置读取：`config`，支持配置文件和环境变量覆盖。
- 日志和追踪：`tracing`、`tracing-subscriber`、`tracing-appender`。
- 加密：优先使用 RustCrypto 生态的 `aes-gcm`；如现场安全合规要求 OpenSSL/FIPS，再切换到 `openssl`。
- 校验：`sha2`。
- UUID 和时间：`uuid`、`chrono`。
- 错误处理：`thiserror`、`anyhow`。业务错误类型用 `thiserror`，入口层和任务主循环可用 `anyhow` 汇总上下文。

不建议第一版引入 ORM、复杂任务队列或额外消息中间件。

### 12.2 PostgreSQL 迁移脚本

推荐使用 `sqlx migrate` 管理迁移，迁移文件按端拆分：

```text
sql/center/
sql/edge/
```

第一版迁移脚本最少包含：

- `0001_init_center.sql`：中控端基础表、唯一约束和必要索引。
- `0001_init_edge.sql`：边缘端基础表、唯一约束和必要索引。
- `0002_seed_required_enum.sql`：插入或约束第一版统一枚举，确保状态码与协议一致。

SQL 注释要求：

- 每个 SQL 文件开头必须备注脚本作用、适用端、创建或修改的主要对象。
- 每张表必须使用 `COMMENT ON TABLE` 备注业务含义。
- 每个字段必须使用 `COMMENT ON COLUMN` 备注字段含义、数据来源和关键约束。
- 每个唯一索引、普通索引和外键约束必须在相邻 SQL 注释中说明用途。
- 如迁移脚本包含函数、触发器或存储过程，必须在定义前备注该方法的作用、触发时机、输入输出和幂等边界。
- 状态字段、枚举字段和布尔字段必须说明可选值含义，避免中控端和边缘端解释不一致。

数据库字段和约束以 [数据库设计.md](数据库设计.md) 为准；迁移脚本必须成为最终实现的唯一落库依据。

### 12.3 前端组件结构

推荐中控端和边缘端分别独立前端工程，组件命名保持一致，便于复用类型和展示习惯。

```text
frontend-center/
  src/
    api/
    stores/
    views/
    components/
      DiskList.vue
      DiskProgressTable.vue
      JobSummary.vue
      ErrorPanel.vue
    ws/

frontend-edge/
  src/
    api/
    stores/
    views/
    components/
      DiskList.vue
      DiskProgressTable.vue
      JobSummary.vue
      ErrorPanel.vue
    ws/
```

第一版页面选择：

- 边缘端：`DashboardView` 一个主页面，展示 RustFS 扫描汇总、运输盘列表、导出任务和异常。
- 中控端：`DashboardView` 一个主页面，展示运输盘注册状态、待导入盘、导入进度和异常。

不建议第一版做复杂路由、权限后台和配置页面；配置先由部署文件完成。

### 12.4 systemd service 文件

推荐拆成两个服务名：

- 中控端：`rustfs-transfer-center.service`。
- 边缘端：`rustfs-transfer-edge.service`。

服务文件统一放在：

```text
deploy/systemd/
```

运行约定：

- 程序目录：`/opt/rustfs-transfer/`。
- 配置目录：`/etc/rustfs-transfer/`。
- 数据和任务运行目录：`/var/lib/rustfs-transfer/`。
- 日志目录：`/var/log/rustfs-transfer/`。
- systemd 启动策略：`Restart=on-failure`，`RestartSec=5s`。

### 12.5 udev 规则文件

推荐使用统一规则文件：

```text
deploy/udev/99-rustfs-transfer-disk.rules
```

第一版不在 udev 规则里直接执行业务导入或导出，只触发 systemd 服务识别磁盘变化。后端服务启动时也必须主动扫描已有磁盘，防止服务重启或 udev 事件丢失导致漏盘。

### 12.6 配置文件和环境变量

推荐使用 TOML 配置文件，按端拆分：

```text
/etc/rustfs-transfer/center.toml
/etc/rustfs-transfer/edge.toml
```

环境变量统一使用 `RUSTFS_TRANSFER__` 前缀，双下划线表示层级覆盖，例如：

```text
RUSTFS_TRANSFER__SERVER__BIND=0.0.0.0:8080
RUSTFS_TRANSFER__DATABASE__URL=postgres://user:pass@127.0.0.1:5432/rustfs_transfer
RUSTFS_TRANSFER__RUSTFS__ENDPOINT=http://127.0.0.1:9000
RUSTFS_TRANSFER__CENTER__BASE_URL=http://center.example.com:8080
```

敏感项优先通过环境变量注入，不写入版本库中的示例配置。

### 12.7 日志路径和保留周期

推荐使用结构化 JSON 日志，按天滚动：

```text
/var/log/rustfs-transfer/center.log
/var/log/rustfs-transfer/edge.log
```

保留策略：

- 本机服务日志默认保留 30 天。
- 运输盘内 `logs/` 只保留本次导出或导入相关日志摘要，不作为长期审计日志。
- 中控端导入账本和任务表才是长期审计依据。

第一版必须保证每条关键日志携带 `request_id`、`job_id`、`disk_id`；对象级日志在处理对象时携带 `bucket`、`object_key`、`etag`。

### 12.8 第一版建议暂缓的选择

以下内容建议放到第二优先级，不影响主流程上线：

- 完整权限管理后台。
- 多租户配置中心。
- 外部 KMS 或 HSM 集成。
- 日志集中采集平台。
- 小文件极多场景下的专门性能调优。
