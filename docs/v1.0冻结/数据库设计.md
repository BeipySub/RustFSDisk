# 数据库设计

本文档记录 RustFS 离线运输盘同步项目的数据库表设计、字段含义和关键约束。

关联文档：

- [需求文档.md](需求文档.md)
- [开发协议契约.md](开发协议契约.md)

## 1. 数据库职责边界

中控端数据库是权威库，负责：

- 运输盘注册。
- 边缘端注册。
- 运输盘注册和启用状态。
- 运输盘数据加密密钥。
- 中控归档 bucket。
- 导入任务。
- 全局对象去重账本。

边缘端数据库是本地运行账本，负责：

- RustFS 对象扫描快照。
- 导出任务。
- 导出对象状态。
- 本地运输盘运行状态。
- 程序重启后的恢复。
- 边缘前端实时展示数据来源。

关键原则：

- 中控端最终导入判断只认中控数据库和运输盘协议。
- 边缘端不可直接修改中控导入账本。
- 边缘端查询中控已导入对象只是优化，不是强依赖。
- 中控端不可达但边缘端已完成硬盘校验并已领取本次 `disk_data_key` 时，边缘端可继续基于本地账本导出；如果尚未领取数据加密密钥，则不得开始新的加密导出。

数据库时间规则：

- 所有 `timestamp` 字段统一保存 UTC 时间。
- 写入格式为 ISO8601 UTC，例如 `2026-08-08T06:30:00Z`。
- 数据库不得保存本地时区时间；前端展示时再转换为用户本地时间。
- 从 RustFS/S3 获取的 `last_modified` 也必须归一化为 UTC 后再入库。

## 2. 数据库表总览

| 所属端 | 表名 | 中文名称 | 表含义 | 主要用途 |
|---|---|---|---|---|
| 中控端 | `disk_list` | 运输盘注册表 | 记录中控端登记过的运输硬盘。该表只判断硬盘是否注册、是否启用，不记录运输盘生命周期。 | 边缘端插盘后向中控校验硬盘是否允许使用。 |
| 中控端 | `edge_site` | 边缘站点表 | 记录所有边缘端站点的注册信息。 | 判断边缘端是否允许接入中控端，并生成对应归档 bucket。 |
| 中控端 | `signature_key` | 中控协议签名密钥表 | 记录 `disk_info.json` 中控签名密钥元数据。 | 中控初始化和重新初始化时生成 `center_signature`；中控端校验协议基础字段和密钥绑定字段。 |
| 中控端 | `data_key` | 数据加密密钥表 | 记录运输盘对象数据落盘加密密钥。 | 中控端初始化运输盘、边缘端导出取密钥、中控端导入解密。 |
| 中控端 | `import_job` | 导入任务表 | 记录中控端每次导入运输盘的任务进度和结果。 | 展示导入进度、失败恢复、防止重复启动导入任务。 |
| 中控端 | `chunk_import_group` | 跨盘分块导入组表 | 记录一个跨盘大对象在中控端的聚合状态。 | 等待多个运输盘分块到齐、校验整体连续性、控制合并导入幂等。 |
| 中控端 | `chunk_import_part` | 跨盘分块明细表 | 记录跨盘大对象每个分块来自哪块运输盘和哪个导入任务。 | 防止分块重复、追踪缺失分块、支持断点恢复。 |
| 中控端 | `object_ledger` | 对象导入账本表 | 记录已经成功导入中控 RustFS 的对象。 | 全局去重、幂等导入、对象来源追踪。 |
| 边缘端 | `local_object_snapshot` | 本地对象快照表 | 记录边缘端扫描 RustFS 得到的对象快照。 | 对象统计、稳定性判断、导出任务编排。 |
| 边缘端 | `export_job` | 导出任务表 | 记录边缘端一次导出任务的阶段状态、低频 checkpoint 和结果。 | 失败恢复、多盘任务管理、页面首次加载状态恢复。 |
| 边缘端 | `export_object` | 导出对象任务表 | 记录每个对象在导出任务中的分配、拷贝和结果状态。 | 多盘并行对象分配锁、对象生命周期、断点恢复。 |
| 边缘端 | `disk_runtime` | 运输盘运行状态表 | 记录边缘端当前识别到的运输盘运行信息。 | 热插拔展示、任务调度、盘级状态和低频 checkpoint。 |

## 3. 中控端数据库

### 3.1 disk_list

表用途：记录中控端注册过的运输盘，是边缘端校验运输盘是否已授权、是否启用、是否允许使用的权威表。

| 字段名 | 类型 | 是否必填 | 字段说明 | 备注/约束 |
|---|---|---|---|---|
| `id` | bigint | 是 | 数据库主键 | 使用自增 bigint。 |
| `sn` | varchar | 是 | 运输盘硬件序列号 | 中控端读取硬盘得到；可建唯一索引；如现场存在 USB 转接盒导致 SN 不稳定，以 `disk_id` 作为最终协议身份。 |
| `disk_id` | varchar/uuid | 是 | 中控生成的运输盘逻辑 ID | 两端协议使用的稳定 ID；必须唯一。 |
| `capacity_bytes` | bigint | 否 | 最近一次初始化识别到的运输盘总容量 | 写入 `disk_info.json.disk.capacity_bytes`；边缘端运行时仍以 `disk_runtime.capacity_bytes` 为当前检测值。 |
| `status` | boolean | 是 | 是否启用 | `true` 表示该运输盘已启用，边缘端校验时允许使用；`false` 表示该运输盘被禁用，边缘端校验时必须拒绝使用。 |
| `create_time` | timestamp | 是 | 创建时间 | 运输盘首次录入中控的 UTC 时间。 |
| `last_init_time` | timestamp | 否 | 最近一次初始化时间 | 中控格式化并写入 `disk_info.json` 后更新，保存 UTC 时间。 |
| `remark` | text | 否 | 备注 | 人工填写，例如硬盘编号、位置、负责人。 |

关键约束：

- `disk_id` 必须唯一。
- `sn` 可建唯一索引；如现场 SN 不稳定，应以 `disk_id` 作为最终协议身份。
- `status` 只表示运输盘是否启用，不表示运输盘生命周期。
- `disk_info.json.status.code` 在 API 中统一命名为 `status_code` 或 `expected_status`，不得映射到 `disk_list.status`。
- `disk_list.status` 在 API 中只能映射为 `disk_enabled` 或 `enabled`，不得序列化为裸 `status`。
- `status = true` 时，边缘端可继续校验运输盘协议文件和 `disk_info.json.status.code`。
- `status = false` 时，边缘端必须拒绝使用该运输盘。
- 运输盘生命周期状态以运输盘内 `disk_info.json.status.code` 为准，不写入 `disk_list.status`。
- 运输盘文件系统强制固定为 `ext4`，文件系统校验以当前物理盘运行时检测结果为准，非 `ext4` 必须拒绝。

### 3.2 edge_site

表用途：记录所有边缘站点注册信息，用于鉴权、归档 bucket 命名和来源追踪。

| 字段名 | 类型 | 是否必填 | 字段说明 | 备注/约束 |
|---|---|---|---|---|
| `id` | bigint | 是 | 数据库主键 | 使用自增 bigint。 |
| `edge_code` | varchar | 是 | 边缘站点编码 | 全局唯一；注册阶段保证满足 S3 bucket 命名要求。 |
| `edge_name` | varchar | 是 | 边缘站点名称 | 前端展示用。 |
| `auth_key_id` | varchar | 是 | 授权密钥编号 | 用于边缘端调用中控端 HTTP API 鉴权；不直接用于运输盘文件加密。 |
| `auth_secret_ciphertext` | text | 是 | HTTP 鉴权密钥密文 | 保存边缘端调用中控 API 的 `edge_auth_secret` 加密值；使用中控本机主密钥或部署环境密钥加密后入库，不得明文落库，不得用于运输盘文件加密。 |
| `status` | varchar | 是 | 边缘站点状态 | `ACTIVE` 表示启用，允许调用中控端接口；`DISABLED` 表示禁用，不允许通过中控端鉴权；`ERROR` 表示异常，默认不允许通过中控端鉴权。 |
| `create_time` | timestamp | 是 | 创建时间 | 站点首次注册 UTC 时间。 |

关键约束：

- `edge_code` 必须唯一。
- `auth_key_id` 必须唯一。
- `auth_key_id` 和 `auth_secret_ciphertext` 只允许在边缘站点首次注册时写入；注册后禁止重置、替换或轮换。
- `auth_secret_ciphertext` 只用于中控端校验 HTTP HMAC 请求签名，不得复用为 `disk_data_key`、`signature_key` 或其他运输盘落盘加密材料。
- 中控端验签时，必须通过 `X-Edge-Code` 找到 `edge_site`，确认 `X-Auth-Key-Id = edge_site.auth_key_id`，再解密该行的 `auth_secret_ciphertext` 得到 `edge_auth_secret` 校验 HMAC。
- API 请求级 nonce 防重放不新增数据库表；中控端必须在进程内维护 `X-Auth-Key-Id + X-Nonce` 的 TTL 缓存，保存时间不得少于 10 分钟。
- 中控归档 bucket 固定按 `archive-{edge_code}` 生成。
- 禁用或异常状态的边缘端不得通过中控 SN 校验和导出校验。
- `edge_site.status` 在 API 中只能映射为 `edge_status`，不得序列化为裸 `status`。

### 3.3 signature_key

表用途：记录中控端协议文件签名密钥元数据。签名密钥只用于生成和校验 `disk_info.json.security.center_signature`，不下发给边缘端，不用于边缘封盘签名。

| 字段名 | 类型 | 是否必填 | 字段说明 | 备注/约束 |
|---|---|---|---|---|
| `id` | bigint | 是 | 数据库主键 | 使用自增 bigint。 |
| `key_id` | varchar/uuid | 是 | 中控签名密钥编号 | 写入 `disk_info.json.security.center_key_id`；不得与 `data_key.data_key_id` 混用。 |
| `owner_type` | varchar | 是 | 密钥所属方类型 | 固定为 `CENTER`。 |
| `owner_code` | varchar | 是 | 密钥所属方编码 | 填部署配置中的 `center_id` / 中控系统 ID。 |
| `signature_alg` | varchar | 是 | 签名算法 | 固定为 `HMAC-SHA256`，对应 `disk_info.json.security.signature_alg`。 |
| `encrypted_key` | text/blob | 是 | 加密后的签名密钥 | 不保存明文；使用中控本机主密钥或部署环境密钥加密后入库。 |
| `status` | varchar | 是 | 密钥状态 | `ACTIVE` 表示可用于签名和验签；`DISABLED` 表示停用；`REVOKED` 表示吊销。 |
| `create_time` | timestamp | 是 | 创建时间 | 生成签名密钥的 UTC 时间。 |
| `retire_time` | timestamp | 否 | 退役时间 | 密钥停用或轮换后写入。 |
| `last_use_time` | timestamp | 否 | 最近使用时间 | 签名或验签时更新。 |

关键约束：

- `key_id` 必须唯一。
- `auth_key_id` 只用于 HTTP API 鉴权，不得复用为 `signature_key.key_id`。
- `data_key_id` 只用于 AES-256-GCM 数据加密，不得复用为 `signature_key.key_id`。
- 边缘端不得持有、领取或使用 `signature_key` 中的中控签名密钥。

### 3.4 data_key

表用途：记录运输盘对象数据落盘加密密钥。该表只存在于中控端，运输盘和边缘端数据库不得保存明文数据密钥。

| 字段名 | 类型 | 是否必填 | 字段说明 | 备注/约束 |
|---|---|---|---|---|
| `id` | bigint | 是 | 数据库主键 | 使用自增 bigint。 |
| `data_key_id` | varchar/uuid | 是 | 数据加密密钥编号 | 写入 `disk_info.json.security.data_key_id` 和 manifest；必须唯一。 |
| `disk_id` | varchar/uuid | 是 | 关联运输盘逻辑 ID | 表示该密钥当前绑定的运输盘。 |
| `edge_code` | varchar | 否 | 允许使用该密钥的边缘站点编码 | 运输盘交付给边缘端前可为空；导出授权后必须写入。 |
| `export_job_id` | varchar/uuid | 否 | 关联边缘端导出任务 ID | 边缘端开始导出后绑定，用于审计和防止密钥跨任务误用。 |
| `seal_id` | varchar/uuid | 否 | 封盘批次 ID | 边缘端封盘后绑定；用于审计该密钥对应的封盘批次。 |
| `encryption_alg` | varchar | 是 | 数据加密算法 | 固定为 `AES-256-GCM`；对应 `disk_info.json.security.encryption_alg` 和 API `encryption_alg`。 |
| `encrypted_key` | text/blob | 是 | 加密后的 256-bit 数据密钥 | 不保存明文；使用中控本机主密钥或部署环境密钥加密后入库。 |
| `key_wrap_alg` | varchar | 是 | 密钥包裹算法 | 说明 `encrypted_key` 如何被保护，例如 `LOCAL-MASTER-KEY` 或后续 KMS 算法。 |
| `status` | varchar | 是 | 密钥状态 | `ACTIVE`、`ISSUED`、`SEALED_READONLY`、`RETIRED`、`REVOKED`。 |
| `create_time` | timestamp | 是 | 创建时间 | 中控端初始化运输盘并生成密钥的 UTC 时间。 |
| `activate_time` | timestamp | 否 | 启用时间 | 密钥允许被边缘端领取的 UTC 时间。 |
| `issued_time` | timestamp | 否 | 发放时间 | 首次向边缘端返回明文 `disk_data_key` 的 UTC 时间。 |
| `sealed_time` | timestamp | 否 | 封盘时间 | 密钥进入 `SEALED_READONLY` 的 UTC 时间。 |
| `retire_time` | timestamp | 否 | 退役时间 | 运输盘完成导入并重新初始化后可标记退役，保存 UTC 时间；历史导入审计仍需保留。 |
| `last_use_time` | timestamp | 否 | 最近使用时间 | 中控端发放密钥或导入解密时更新，保存 UTC 时间。 |
| `remark` | text | 否 | 备注 | 记录人工说明或异常原因。 |

关键约束：

- `data_key_id` 必须唯一。
- 运输盘和 manifest 只能保存 `data_key_id`，不得保存 `encrypted_key` 或明文 `disk_data_key`。
- `disk_data_key` 不按时间过期，表中不设计 `expires_at`；密钥有效性跟随运输盘生命周期和封盘批次。
- 中控端向边缘端返回明文 `disk_data_key` 前，必须校验 `edge_code`、`disk_id`、`data_key_id`、盘内 `status.code`、边缘端授权和 `data_key.status`。
- 只有 `ACTIVE` 或已绑定同一 `edge_code + export_job_id` 的 `ISSUED` 状态允许向边缘端发放明文 `disk_data_key`。
- `SEALED_READONLY`、`RETIRED`、`REVOKED` 均不得再发给边缘端用于导出写盘。
- 导入已封盘运输盘时，`ACTIVE`、`ISSUED`、`SEALED_READONLY`、`RETIRED` 均允许中控端按 `data_key_id` 解密；其中 `RETIRED` 仅用于历史审计、重复插盘幂等校验或人工恢复。
- `REVOKED` 表示密钥疑似泄露或人工吊销，默认不得发放也不得自动解密；确需历史解密必须人工审批并记录审计日志。
- 边缘端封盘后，中控端在下一次看到该盘或导入前，必须将对应密钥更新为 `SEALED_READONLY`，并把盘内 `disk_info.json.edge.seal_id` 写入 `data_key.seal_id`。
- 中控端导入完成并重新初始化运输盘后，必须将旧密钥更新为 `RETIRED`，并为新初始化盘生成新的 `data_key_id + disk_data_key`。

密钥状态流转：

```text
ACTIVE
-> ISSUED
-> SEALED_READONLY
-> RETIRED

ACTIVE / ISSUED / SEALED_READONLY
-> REVOKED
```

### 3.5 import_job

表用途：记录中控端每次导入运输盘的任务，用于进度展示、失败恢复和审计。

| 字段名 | 类型 | 是否必填 | 字段说明 | 备注/约束 |
|---|---|---|---|---|
| `id` | bigint | 是 | 数据库主键 | 使用自增 bigint。 |
| `import_job_id` | varchar/uuid | 是 | 导入任务业务 ID | 对外协议、WebSocket、日志和 `object_ledger.import_job_id` 使用该字段，不使用数据库自增主键。 |
| `disk_id` | varchar/uuid | 是 | 当前导入的运输盘逻辑 ID | 关联 `disk_list.disk_id`。 |
| `seal_id` | varchar/uuid | 是 | 封盘批次 ID | 来自 `disk_info.json.edge.seal_id` 和 manifest `seal_id`；同一 `disk_id` 每次封盘必须生成新的 `seal_id`。 |
| `export_job_id` | varchar/uuid | 是 | 边缘端导出任务 ID | 来自 `disk_info.json.edge.export_job_id` 或 manifest `export_job_id`，用于追溯封盘来源。 |
| `manifest_sha256` | varchar | 是 | 清单文件 SHA256 | 来自 `disk_info.json.manifest.manifest_sha256`，用于校验同一封盘批次是否被篡改或混淆。 |
| `edge_code` | varchar | 是 | 来源边缘站点编码 | 来自 `disk_info.json.edge.edge_code`。 |
| `status` | varchar | 是 | 导入任务状态 | `PENDING` 表示待导入；`IMPORTING` 表示导入中；`DONE` 表示导入完成；`FAILED` 表示导入失败；`CANCELLED` 表示已取消。 |
| `object_count` | bigint | 是 | manifest 中有效对象或分块条目总数 | 用于前端展示本盘处理条目数。 |
| `imported_count` | bigint | 是 | 已成功导入对象数 | 每成功导入一个对象后更新。 |
| `total_bytes` | bigint | 是 | manifest 中有效对象总字节数 | 用于计算导入总进度。 |
| `imported_bytes` | bigint | 是 | 已成功导入字节数 | 用于计算导入进度和剩余字节。 |
| `start_time` | timestamp | 否 | 导入开始时间 | 状态变为 `IMPORTING`（导入中）时写入 UTC 时间。 |
| `finish_time` | timestamp | 否 | 导入结束时间 | 状态变为 `DONE`（导入完成）、`FAILED`（导入失败）或 `CANCELLED`（已取消）时写入 UTC 时间。 |
| `error_message` | text | 否 | 失败原因 | 导入失败时必须写入。 |

关键约束：

- `id` 只作为数据库内部主键，不得写入 `disk_info.json`、manifest、HTTP API、WebSocket 或日志追踪字段。
- `import_job_id` 必须唯一，创建导入任务时生成，跨 API、WebSocket、日志、`chunk_import_part.import_job_id` 和 `object_ledger.import_job_id` 全链路保持一致。
- `seal_id` 必须非空，且必须与盘内 `disk_info.json.edge.seal_id`、manifest 顶层 `seal_id` 一致。
- 同一块盘同一封盘批次不得并发创建多个 `IMPORTING` 任务；并发控制必须使用 `disk_id + seal_id`，不能只使用 `disk_id`。
- 同一 `disk_id + seal_id` 如已存在 `DONE` 任务，且 `manifest_sha256` 一致，再次插入该盘时必须视为重复导入并跳过。
- 同一 `disk_id + seal_id` 如出现不同 `manifest_sha256`，必须拒绝导入并记录 `SEAL_ID_MANIFEST_MISMATCH`。
- 只有本盘全部普通对象完成导入并写入 `object_ledger`，且本盘全部跨盘分块完成登记和校验并写入 `chunk_import_part` 后，当前 `import_job` 才能标记为 `DONE`。
- 跨盘分块所在盘的 `import_job.status = DONE` 只表示该盘分块已被中控端接收和校验，不表示跨盘源对象已经完成归档；跨盘源对象完成状态以 `chunk_import_group.status = DONE` 和 `object_ledger` 为准。
- 任务失败时不得把运输盘写为 `IMPORTED`（已导入）。
- `import_job` 只保存导入任务阶段和最终结果。
- `object_ledger` 只保存对象导入成功账本。
- `import_job.status` 序列化到 WebSocket 或 API 时必须命名为 `import_job_status`，不得使用裸 `status`。

数据库约束：

```sql
CREATE UNIQUE INDEX uq_import_job_seal_active_or_done
  ON import_job(disk_id, seal_id)
  WHERE status IN ('PENDING', 'IMPORTING', 'DONE');

CREATE UNIQUE INDEX uq_import_job_business_id
  ON import_job(import_job_id);

CREATE INDEX idx_import_job_seal_manifest
  ON import_job(disk_id, seal_id, manifest_sha256);
```

说明：`FAILED` 或 `CANCELLED` 不进入 `uq_import_job_seal_active_or_done`，允许同一封盘批次在人工确认后重新创建导入任务；重新创建前必须先查询同一 `disk_id + seal_id` 的历史任务，如果 `manifest_sha256` 不一致，必须拒绝导入。

### 3.6 chunk_import_group

表用途：记录中控端跨盘大对象的分块聚合状态。一个 `chunk_import_group` 对应一个源对象的一组跨盘分块，只有全部分块到齐、校验通过并完成合并上传后，才能写入 `object_ledger`。

| 字段名 | 类型 | 是否必填 | 字段说明 | 备注/约束 |
|---|---|---|---|---|
| `id` | bigint | 是 | 数据库主键 | 使用自增 bigint。 |
| `chunk_group_id` | varchar/uuid | 是 | 分块组 ID | 来自 manifest `objects[].chunk_group_id`；同一源对象的所有分块必须一致。 |
| `edge_code` | varchar | 是 | 来源边缘站点编码 | 来自 manifest。 |
| `source_bucket` | varchar | 是 | 边缘 RustFS 原始 bucket | 来自 manifest。 |
| `source_key` | text | 是 | 边缘 RustFS 原始 object key | 来自 manifest。 |
| `source_etag` | varchar | 是 | 源对象 ETag | 用于对象版本识别和去重。 |
| `source_size_bytes` | bigint | 是 | 源对象总大小 | 必须等于所有分块 `chunk_size_bytes` 之和。 |
| `source_last_modified` | timestamp | 是 | 源对象最后修改时间 | 从 manifest 归一化为 UTC 后写入。 |
| `plaintext_sha256` | varchar | 是 | 源对象整体明文 SHA256 | 所有分块解密合并后必须校验该值。 |
| `chunk_total` | integer | 是 | 分块总数 | 必须满足 `1 < chunk_total <= 1,000,000`。 |
| `received_count` | integer | 是 | 已登记分块数 | 每成功登记一个唯一分块后更新。 |
| `received_bytes` | bigint | 是 | 已登记分块明文字节数 | 用于展示等待进度和恢复。 |
| `status` | varchar | 是 | 聚合状态 | `WAITING_PARTS` 表示等待分块；`READY_TO_MERGE` 表示分块到齐待合并；`MERGING` 表示合并上传中；`DONE` 表示已导入并写账本；`FAILED` 表示聚合或合并失败；`CANCELLED` 表示取消。 |
| `import_bucket` | varchar | 否 | 中控 RustFS 归档 bucket | 分块到齐后导入使用，例如 `archive-site001`。 |
| `import_key` | text | 否 | 中控 RustFS 导入 key | 分块到齐后导入使用，例如 `photos/2026/08/08/a.bin`。 |
| `created_at` | timestamp | 是 | 首次发现分块时间 | 保存 UTC 时间。 |
| `updated_at` | timestamp | 是 | 最近更新时间 | 保存 UTC 时间。 |
| `finish_time` | timestamp | 否 | 合并导入完成时间 | 状态变为 `DONE`、`FAILED` 或 `CANCELLED` 时写入。 |
| `error_code` | varchar | 否 | 失败错误码 | 聚合失败时写入 `MANIFEST_INVALID`、`CHECKSUM_MISMATCH`、`DECRYPT_FAILED`、`NONCE_REUSED` 等标准错误码。 |
| `error_message` | text | 否 | 失败原因 | 状态为 `FAILED` 时必须写入。 |

关键约束：

- `chunk_group_id` 必须唯一。
- 同一 `chunk_group_id` 下所有分块的 `edge_code + source_bucket + source_key + source_etag + source_size_bytes + source_last_modified + plaintext_sha256 + chunk_total` 必须完全一致。
- `received_count = chunk_total` 且分块索引从 `0` 到 `chunk_total - 1` 连续完整时，才能进入 `READY_TO_MERGE`。
- `received_bytes` 必须等于 `source_size_bytes` 后才能进入 `READY_TO_MERGE`。
- `DONE` 状态表示整体对象已上传中控 RustFS 并成功写入 `object_ledger`；单个分块不得写入 `object_ledger` 表达对象已导入。

数据库约束：

```sql
CREATE UNIQUE INDEX uq_chunk_import_group_id
  ON chunk_import_group(chunk_group_id);

CREATE INDEX idx_chunk_import_group_status
  ON chunk_import_group(status, updated_at);
```

### 3.7 chunk_import_part

表用途：记录跨盘大对象每个分块的导入登记和校验结果。中控端每读取到一个 `chunked = true` 的 manifest 对象，必须先登记到该表，再判断对应 `chunk_import_group` 是否到齐。

| 字段名 | 类型 | 是否必填 | 字段说明 | 备注/约束 |
|---|---|---|---|---|
| `id` | bigint | 是 | 数据库主键 | 使用自增 bigint。 |
| `chunk_group_id` | varchar/uuid | 是 | 分块组 ID | 关联 `chunk_import_group.chunk_group_id`。 |
| `chunk_index` | integer | 是 | 当前分块序号 | 从 0 开始。 |
| `chunk_total` | integer | 是 | 分块总数 | 必须与 `chunk_import_group.chunk_total` 一致。 |
| `chunk_offset_bytes` | bigint | 是 | 当前分块在源对象中的起始偏移 | 用于合并顺序校验。 |
| `chunk_size_bytes` | bigint | 是 | 当前分块明文字节数 | 用于总大小校验。 |
| `chunk_sha256` | varchar | 是 | 当前分块密文 SHA256 | 与 manifest `objects[].chunk_sha256` 或 `ciphertext_sha256` 一致。 |
| `ciphertext_sha256` | varchar | 是 | 密文文件 SHA256 | 中控读取分块文件后必须校验。 |
| `plaintext_sha256` | varchar | 是 | 源对象整体明文 SHA256 | 用于和分组表核对。 |
| `data_key_id` | varchar/uuid | 是 | 数据加密密钥编号 | 用于解密和 nonce 唯一性校验。 |
| `nonce` | varchar | 是 | AES-GCM nonce | 同一 `data_key_id + nonce` 在历史导入账本和分块明细中不得重复。 |
| `tag` | varchar | 是 | AES-GCM 认证标签 | 用于认证密文未被篡改。 |
| `aad` | text | 是 | AES-GCM 附加认证数据 | 必须与 manifest 记录一致。 |
| `disk_id` | varchar/uuid | 是 | 分块所在运输盘逻辑 ID | 来自 manifest 顶层 `disk_id`。 |
| `seal_id` | varchar/uuid | 是 | 分块所在运输盘封盘批次 ID | 来自 manifest 顶层 `seal_id`。 |
| `import_job_id` | varchar/uuid | 是 | 登记该分块的导入任务业务 ID | 关联 `import_job.import_job_id`。 |
| `relative_data_path` | text | 是 | 分块密文文件相对路径 | 相对于 `/rustfs-transfer/`，必须位于 `data/` 下。 |
| `staged_ciphertext_path` | text | 是 | 中控端本地暂存密文路径 | 相对于中控端 `/var/lib/rustfs-transfer/chunks/`；分块校验通过后复制到本地暂存区并 `fsync` 成功。 |
| `staged_ciphertext_sha256` | varchar | 是 | 中控端暂存密文 SHA256 | 必须与 `ciphertext_sha256` 一致，用于合并前再次校验暂存文件完整性。 |
| `status` | varchar | 是 | 分块状态 | `REGISTERED`、`VERIFIED`、`MERGED`、`FAILED`。 |
| `registered_at` | timestamp | 是 | 分块登记时间 | 保存 UTC 时间。 |
| `verified_at` | timestamp | 否 | 分块校验完成时间 | 密文 SHA256 和解密认证通过后写入。 |
| `error_code` | varchar | 否 | 失败错误码 | 分块失败时写入标准错误码。 |
| `error_message` | text | 否 | 失败原因 | 状态为 `FAILED` 时必须写入。 |

关键约束：

- 同一 `chunk_group_id + chunk_index` 只能登记一次；重复出现且字段完全一致时按幂等处理，字段不一致时拒绝并记录 `MANIFEST_INVALID`。
- 同一 `data_key_id + nonce` 在 `chunk_import_part` 中必须唯一，并且不得与 `object_ledger` 已导入对象重复。
- 分块进入 `VERIFIED` 前，必须完成路径规范化、密文 SHA256 校验、AES-GCM tag 验证、AAD 校验、本地暂存密文写入和暂存目录 `fsync`。
- 所有分块进入 `VERIFIED` 且 `chunk_import_group.status = READY_TO_MERGE` 后，中控端才能按 `chunk_index` 顺序解密合并并上传中控 RustFS。
- 运输盘封存数据清理前，属于跨盘对象的本盘分块必须已经以 `VERIFIED` 状态持久化到中控端本地暂存区；否则不得清理该运输盘上的分块密文文件。

数据库约束：

```sql
CREATE UNIQUE INDEX uq_chunk_import_part_group_index
  ON chunk_import_part(chunk_group_id, chunk_index);

CREATE UNIQUE INDEX uq_chunk_import_part_data_key_nonce
  ON chunk_import_part(data_key_id, nonce);

CREATE INDEX idx_chunk_import_part_job
  ON chunk_import_part(import_job_id);
```

### 3.8 object_ledger

表用途：中控端全局对象导入账本，是对象去重和审计的最终依据。

| 字段名 | 类型 | 是否必填 | 字段说明 | 备注/约束 |
|---|---|---|---|---|
| `id` | bigint | 是 | 数据库主键 | 使用自增 bigint。 |
| `edge_code` | varchar | 是 | 来源边缘站点编码 | 区分不同边缘端。 |
| `source_bucket` | varchar | 是 | 边缘 RustFS 原始 bucket | 来自 manifest。 |
| `source_key` | text | 是 | 边缘 RustFS 原始 object key | 来自 manifest，必须保持原值。 |
| `source_etag` | varchar | 是 | 源对象 ETag | 用于对象版本识别和去重参考。 |
| `source_size_bytes` | bigint | 是 | 源对象大小，单位字节 | 用于去重和校验。 |
| `source_last_modified` | timestamp | 是 | 源对象最后修改时间 | 从 RustFS/S3 获取后归一化为 UTC，用于识别同名覆盖对象。 |
| `plaintext_sha256` | varchar | 是 | 源对象明文 SHA256 | 边缘端流式读取源对象时同步计算；中控端解密后可再次计算并比对，用于审计和内容完整性校验。 |
| `ciphertext_sha256` | varchar | 否 | 运输盘密文文件 SHA256 | 中控导入前校验运输盘文件完整性；来自 manifest。 |
| `chunk_group_id` | varchar/uuid | 否 | 跨盘分块组 ID | 普通对象为空；跨盘对象必填，来自 manifest `objects[].chunk_group_id`，用于表达多个分块合并后的同一个源对象。 |
| `data_key_id` | varchar/uuid | 否 | 数据加密密钥编号 | 普通对象必填，来自 manifest `objects[].data_key_id`；跨盘对象在 `chunk_import_part` 中逐分块记录。 |
| `nonce` | varchar | 否 | AES-GCM nonce | 普通对象必填，来自 manifest `objects[].nonce`；跨盘对象在 `chunk_import_part` 中逐分块记录。 |
| `import_bucket` | varchar | 是 | 中控 RustFS 归档 bucket | 例如 `archive-site001`。 |
| `import_key` | text | 是 | 中控 RustFS 导入 key | 例如 `photos/2026/08/08/a.jpg`。 |
| `export_job_id` | varchar/uuid | 是 | 边缘端导出任务 ID | 来自 manifest 或 `disk_info.json`。 |
| `import_job_id` | varchar/uuid | 是 | 中控端导入任务业务 ID | 关联 `import_job.import_job_id`。 |
| `imported_at` | timestamp | 是 | 导入完成时间 | 对象上传成功且账本写入成功的 UTC 时间。 |

关键约束：

- 必须唯一键：`edge_code + source_bucket + source_key + source_etag + source_size_bytes + source_last_modified`。
- 普通对象必须写入 `data_key_id + nonce`，并受 `data_key_id + nonce` 唯一键约束，用于防止同一 AES-GCM 数据密钥下 nonce 被重复导入。
- 跨盘对象必须写入 `chunk_group_id`，不得把任一分块的 `data_key_id + nonce` 当作整体对象账本的 nonce；跨盘分块 nonce 唯一性由 `chunk_import_part` 负责。
- 对象上传到中控 RustFS 成功后，才能写入 `object_ledger`。
- `object_ledger` 不增加对象导入中间状态字段；只保存已上传成功的对象记录。
- 重复导入时，如果唯一键已存在，必须跳过该对象。
- 并发导入时，如果对象上传成功后写入 `object_ledger` 发生唯一键冲突，必须视为其他 Worker 已完成同一来源对象版本入账，当前 Worker 不得再写重复账本。
- 中控端最终去重必须以该表为准。

数据库约束：

```sql
CREATE UNIQUE INDEX uq_object_ledger_data_key_nonce
  ON object_ledger(data_key_id, nonce)
  WHERE data_key_id IS NOT NULL AND nonce IS NOT NULL;

CREATE UNIQUE INDEX uq_object_ledger_chunk_group
  ON object_ledger(chunk_group_id)
  WHERE chunk_group_id IS NOT NULL;

CREATE UNIQUE INDEX uq_object_ledger_source_version
  ON object_ledger(edge_code, source_bucket, source_key, source_etag, source_size_bytes, source_last_modified);
```

## 4. 边缘端数据库

### 4.1 local_object_snapshot

表用途：记录边缘端最近一次扫描 RustFS 得到的对象快照，用于稳定性判断、任务编排和前端统计。

| 字段名 | 类型 | 是否必填 | 字段说明 | 备注/约束 |
|---|---|---|---|---|
| `id` | bigint | 是 | 数据库主键 | 使用自增 bigint。 |
| `bucket` | varchar | 是 | 边缘 RustFS bucket 名称 | 来自 S3 List。 |
| `object_key` | text | 是 | 边缘 RustFS object key | 来自 S3 List。 |
| `etag` | varchar | 是 | 对象 ETag | 来自 S3 HEAD/List。 |
| `size_bytes` | bigint | 是 | 对象大小，单位字节 | 用于容量编排和进度计算。 |
| `last_modified` | timestamp | 是 | 对象最后修改时间 | 从 RustFS/S3 获取后归一化为 UTC，用于稳定性判断。 |
| `metadata_json` | json/jsonb | 否 | 对象元数据 | 来自 S3 HEAD，用于导出 meta sidecar。 |
| `scanned_at` | timestamp | 是 | 扫描时间 | 记录本次快照生成的 UTC 时间。 |
| `stable_status` | varchar | 是 | 稳定性判断状态 | `UNKNOWN` 表示未知，尚未完成稳定性判断；`STABLE` 表示稳定，可以进入导出队列；`UNSTABLE` 表示不稳定，暂不导出；`SOURCE_CHANGED` 表示源对象发生变化，本轮不导出。 |

关键约束：

- 索引：`bucket + object_key`。
- 对象进入导出队列前，必须通过稳定性判断。
- 同名对象覆盖时，应以 `etag + size_bytes + last_modified` 区分不同版本。

### 4.2 export_job

表用途：记录边缘端一次导出任务，可能对应一块或多块运输盘。

| 字段名 | 类型 | 是否必填 | 字段说明 | 备注/约束 |
|---|---|---|---|---|
| `id` | bigint | 是 | 数据库主键 | 使用自增 bigint。 |
| `export_job_id` | varchar/uuid | 是 | 导出任务业务 ID | 对外协议、WebSocket、日志、manifest、`disk_info.json.edge.export_job_id` 和 `export_object.export_job_id` 使用该字段，不使用数据库自增主键。 |
| `disk_id` | varchar/uuid | 否 | 运输盘逻辑 ID | 单盘任务可填；多盘任务通过 `export_object.disk_id` 关联。 |
| `edge_code` | varchar | 是 | 当前边缘站点编码 | 来自部署配置。 |
| `status` | varchar | 是 | 导出任务状态 | `PENDING` 表示待处理；`SCANNING` 表示扫描中；`COPYING` 表示拷贝中；`SEALED` 表示已封盘；`FAILED` 表示导出失败；`CANCELLED` 表示已取消。 |
| `object_count` | bigint | 是 | 本次任务对象总数 | 调度完成后写入。 |
| `copied_count` | bigint | 是 | 已成功导出对象数 | 对象状态变为 `EXPORTED` 后累加。 |
| `total_bytes` | bigint | 是 | 本次任务总字节数 | 所有已分配对象大小总和。 |
| `copied_bytes` | bigint | 是 | 已成功拷贝字节数 | 任务级低频 checkpoint 和恢复展示使用；运行中 WebSocket 实时进度必须来自内存 `ProgressAggregator`。 |
| `start_time` | timestamp | 否 | 任务开始时间 | 状态进入 `COPYING`（拷贝中）时写入 UTC 时间。 |
| `finish_time` | timestamp | 否 | 任务结束时间 | 状态进入 `SEALED`（已封盘）、`FAILED`（导出失败）或 `CANCELLED`（已取消）时写入 UTC 时间。 |
| `error_message` | text | 否 | 失败原因 | 任务失败时必须写入。 |

关键约束：

- `id` 只作为数据库内部主键，不得写入 `disk_info.json`、manifest、HTTP API、WebSocket 或日志追踪字段。
- `export_job_id` 必须唯一，创建导出任务时生成，跨 API、WebSocket、日志、manifest、`data_key.export_job_id` 和 `export_object.export_job_id` 全链路保持一致。
- 多盘并行时，一个 `export_job` 可以包含多个 `disk_id` 的对象任务。
- 只有所有参与运输盘都完成封盘后，任务才能整体标记为 `SEALED`。
- `export_job` 只保存任务阶段、低频 checkpoint 和最终结果。
- `copied_count`、`copied_bytes` 允许按低频 checkpoint 更新，触发条件为距离上次更新 >= 1 秒、距离上次更新已完成 >= 100 个对象、任务完成、任务失败或任务取消。
- `export_job.status` 序列化到 WebSocket 或 API 时必须命名为 `export_job_status`，不得使用裸 `status`。

数据库约束：

```sql
CREATE UNIQUE INDEX uq_export_job_business_id
  ON export_job(export_job_id);
```

### 4.3 export_object

表用途：记录每个对象在边缘端导出任务中的状态，是多盘并行对象分配锁和断点恢复的核心表。

| 字段名 | 类型 | 是否必填 | 字段说明 | 备注/约束 |
|---|---|---|---|---|
| `id` | bigint | 是 | 数据库主键 | 使用自增 bigint。 |
| `export_job_id` | varchar/uuid | 是 | 所属导出任务业务 ID | 关联 `export_job.export_job_id`。 |
| `disk_id` | varchar/uuid | 否 | 被分配到的运输盘逻辑 ID | `PENDING` 时可为空；进入 `ASSIGNED`、`COPYING`、`EXPORTED` 后必须有值。 |
| `bucket` | varchar | 是 | 源对象 bucket | 来自边缘 RustFS。 |
| `object_key` | text | 是 | 源对象 object key | 来自边缘 RustFS。 |
| `etag` | varchar | 是 | 源对象 ETag | 用于稳定性判断和去重。 |
| `size_bytes` | bigint | 是 | 源对象大小，单位字节 | 用于容量编排和进度计算。 |
| `last_modified` | timestamp | 是 | 源对象最后修改时间 | 从 RustFS/S3 获取后归一化为 UTC，用于判断同名对象是否变化。 |
| `plaintext_sha256` | varchar | 否 | 源对象明文 SHA256 | 边缘端流式读取源对象时同步计算；用于 manifest 和中控导入后校验。 |
| `ciphertext_sha256` | varchar | 否 | 密文文件 SHA256 | 使用 AES-256-GCM 写入运输盘后计算；写入 manifest 的 `ciphertext_sha256`。 |
| `ciphertext_size_bytes` | bigint | 否 | 密文文件大小 | 用于容量统计、进度展示和导入校验。 |
| `encrypted` | boolean | 是 | 是否已落盘加密 | 固定为 `true`。 |
| `encryption_alg` | varchar | 否 | 加密算法 | 固定为 `AES-256-GCM`；未开始拷贝前可为空。 |
| `data_key_id` | varchar/uuid | 否 | 数据加密密钥编号 | 来自 `disk_info.json.security.data_key_id`，写入 manifest；不保存明文密钥。 |
| `nonce` | varchar | 否 | AES-GCM nonce | 每个对象或每个分块唯一；用于中控端解密。 |
| `tag` | varchar | 否 | AES-GCM 认证标签 | 用于中控端认证密文未被篡改。 |
| `aad` | text | 否 | AES-GCM 附加认证数据 | 由 `disk_id/export_job_id/bucket/object_key/chunk_index/chunk_total` 组成。 |
| `chunked` | boolean | 是 | 是否为跨盘分块对象 | `false` 表示普通对象；`true` 表示该记录是对象的一个分块。 |
| `chunk_group_id` | varchar/uuid | 否 | 分块组 ID | 同一个源对象被拆成多个分块时，所有分块使用同一个 `chunk_group_id`。普通对象可为空。 |
| `chunk_index` | integer | 是 | 当前分块序号 | 从 0 开始；普通对象固定为 0；必须满足 `0 <= chunk_index < chunk_total`。 |
| `chunk_total` | integer | 是 | 总分块数量 | 普通对象固定为 1；最大值为 `1,000,000`。 |
| `chunk_offset_bytes` | bigint | 是 | 当前分块在源对象中的起始偏移 | 普通对象固定为 0；跨盘合并时用于按顺序恢复原对象。 |
| `chunk_size_bytes` | bigint | 是 | 当前分块明文大小 | 普通对象等于 `size_bytes`；跨盘分块时为该分块对应的明文字节数。 |
| `chunk_sha256` | varchar | 否 | 当前分块密文 SHA256 | 与 `ciphertext_sha256` 含义一致，保留该字段是为了 manifest 分块字段命名清晰。 |
| `partial_path` | text | 否 | `.partial` 临时密文文件路径 | `COPYING` 状态写入；必须是相对于 `/rustfs-transfer/` 的相对路径，成功原子重命名后清空或保留历史路径供审计，但不得写入 manifest。 |
| `relative_data_path` | text | 否 | 对象密文文件相对路径 | 相对于 `/rustfs-transfer/`，必须位于 `data/` 下，写入 manifest 使用。 |
| `relative_meta_path` | text | 否 | 对象 metadata sidecar 相对路径 | 相对于 `/rustfs-transfer/`，必须位于 `meta/` 下，写入 manifest 使用。 |
| `status` | varchar | 是 | 对象任务状态 | `PENDING` 表示待分配；`ASSIGNED` 表示已分配到运输盘；`COPYING` 表示拷贝中；`EXPORTED` 表示已导出；`FAILED` 表示失败；`SOURCE_CHANGED` 表示源对象变化；`SKIPPED` 表示已跳过。边缘端对象状态不包含 `IMPORTED`。 |
| `error_code` | varchar | 否 | 失败错误码 | `FAILED`、`SOURCE_CHANGED`、`SKIPPED` 时写入标准错误码，例如 `SOURCE_CHANGED`、`DISK_FULL`、`INSUFFICIENT_SPACE`、`PARTIAL_CLEAN_FAILED`、`CHECKSUM_MISMATCH`、`DECRYPT_FAILED`。 |
| `error_message` | text | 否 | 失败原因 | `FAILED`（失败）、`SOURCE_CHANGED`（源对象变化）、`SKIPPED`（已跳过）时必须写入。 |

关键约束：

- 普通对象必须有活动态唯一键：`export_job_id + bucket + object_key + etag + size_bytes + last_modified`，用于防止同一普通对象在同一导出任务中被重复分配到多块运输盘。
- 分块对象必须有活动态唯一键：`export_job_id + bucket + object_key + etag + size_bytes + last_modified + chunk_index`，用于防止同一源对象的同一分块被重复分配。
- 跨盘分块默认大小固定为 `10 GiB`，即 `10,737,418,240 bytes`；除最后一个分块外，所有分块 `chunk_size_bytes` 必须等于 `10 GiB`，最后一个分块可以小于或等于 `10 GiB`。
- `chunk_total` 必须小于或等于 `1,000,000`；超过时边缘端必须拒绝导出该对象并记录错误码 `CHUNK_INDEX_OVERFLOW`。
- AES-GCM nonce 必须唯一：同一 `data_key_id + nonce` 在 `export_object` 中不得重复；如果插入冲突，边缘端必须重新生成 nonce，不得继续使用冲突值加密。
- 对象分配给运输盘时，必须在同一个 PostgreSQL 事务内使用 `SELECT ... FOR UPDATE SKIP LOCKED` 锁定 `PENDING` 行，并通过 `UPDATE ... RETURNING` 原子更新为 `ASSIGNED`（已分配）。只有 `RETURNING` 返回的对象或分块允许 Worker 写盘。
- 如果 `UPDATE ... RETURNING` 返回空结果、唯一索引冲突或事务提交失败，Worker 必须视为未获得分配锁，不得继续拷贝该对象。
- 对象下载时必须流式加密写 `.partial` 临时密文文件，并写入 `partial_path`；成功写入 metadata、完成校验、`fsync` 并原子重命名为最终密文文件后，才能改为 `EXPORTED`（已导出）。
- `COPYING` 过程中的当前对象字节进度、速度、剩余字节数、分盘进度和全局进度必须由内存 `ProgressAggregator` 维护。
- `export_object.status` 的关键状态变更必须立即事务写入，包括 `ASSIGNED`、`COPYING`、`EXPORTED`、`FAILED`、`SOURCE_CHANGED`、`SKIPPED`。
- 写 `.partial`、metadata、manifest 或协议文件时发生 `ENOSPC` 必须记录 `DISK_FULL`；当前对象或分块改为 `FAILED`，删除或隔离 `.partial` 后重新计算 `free_bytes`。
- 对象下载前后 HEAD 结果不一致时，必须写入 `status = SOURCE_CHANGED` 和 `error_code = SOURCE_CHANGED`；该对象不得进入有效 manifest。
- 只有 `EXPORTED`（已导出）对象允许进入 `export_manifest.json`。
- `partial_path`、`relative_data_path`、`relative_meta_path` 不得以 `/` 开头，不得包含 `..`，不得越过 `/rustfs-transfer/` 协议根目录；违反时不得写入 manifest，错误码 `MANIFEST_INVALID`。
- 边缘端本地 `export_object.status` 不得写入 `IMPORTED`；中控是否已导入只由中控端 `object_ledger` / `import_job` 或只读按需查询接口表达。
- `export_object.status` 序列化到 WebSocket 或 manifest 时必须命名为 `object_status`，不得使用裸 `status`。
- 同一个 `chunk_group_id` 下必须满足 `chunk_index` 从 0 到 `chunk_total - 1` 连续完整。
- 同一个 `chunk_group_id` 下必须满足 `chunk_offset_bytes` 从 0 开始按 `chunk_index` 连续递增，后一分块偏移必须等于前一分块偏移加前一分块大小。
- 同一个 `chunk_group_id` 下所有 `chunk_size_bytes` 之和必须等于源对象 `size_bytes`。
- 中控端导入跨盘分块对象时，必须等全部分块均为有效 `EXPORTED` 且校验通过后，才能合并导入。

必须数据库约束：

```sql
CREATE UNIQUE INDEX uq_export_object_plain_active_source
  ON export_object(export_job_id, bucket, object_key, etag, size_bytes, last_modified)
  WHERE chunked = false
    AND status IN ('PENDING', 'ASSIGNED', 'COPYING', 'EXPORTED');

CREATE UNIQUE INDEX uq_export_object_chunk_active_source
  ON export_object(export_job_id, bucket, object_key, etag, size_bytes, last_modified, chunk_index)
  WHERE chunked = true
    AND status IN ('PENDING', 'ASSIGNED', 'COPYING', 'EXPORTED');

CREATE UNIQUE INDEX uq_export_object_data_key_nonce
  ON export_object(data_key_id, nonce)
  WHERE data_key_id IS NOT NULL AND nonce IS NOT NULL;

CREATE UNIQUE INDEX uq_export_object_chunk_group_index
  ON export_object(chunk_group_id, chunk_index)
  WHERE chunked = true AND chunk_group_id IS NOT NULL;
```

对象分配事务必须使用以下 PostgreSQL 语义：

```sql
BEGIN;

WITH candidate AS (
  SELECT id
       , chunk_size_bytes
  FROM export_object
  WHERE export_job_id = :export_job_id
    AND status = 'PENDING'
    AND disk_id IS NULL
    AND chunk_size_bytes <= :object_budget_bytes
  ORDER BY id ASC
  FOR UPDATE SKIP LOCKED
  LIMIT :candidate_limit
),
picked AS (
  SELECT id
  FROM (
    SELECT id,
           SUM(chunk_size_bytes) OVER (ORDER BY id ASC) AS running_bytes
    FROM candidate
  ) AS ranked
  WHERE running_bytes <= :object_budget_bytes
  LIMIT :batch_size
)
UPDATE export_object AS eo
SET status = 'ASSIGNED',
    disk_id = :disk_id
FROM picked
WHERE eo.id = picked.id
RETURNING eo.id, eo.bucket, eo.object_key, eo.chunked, eo.chunk_group_id, eo.chunk_index, eo.chunk_size_bytes;

COMMIT;
```

约束说明：

- `FOR UPDATE SKIP LOCKED` 用于让多个 DiskWorker 并发抢任务时跳过已被其他事务锁定的行。
- 事务提交前，其他按本规则执行抢占的 Worker 会跳过已被锁定的行；事务回滚后，这些行仍保持 `PENDING`，可被重新抢占。
- 批量分配时，事务内返回的对象或分块总大小不得超过当前运输盘重新计算后的 `object_budget_bytes`。
- 应用层不得先在事务外查询 `PENDING` 再逐条更新；该写法会产生重复分配窗口。
- `FAILED`、`SOURCE_CHANGED`、`SKIPPED` 不进入活动态唯一索引；需要重试时应优先复用原记录并把状态改回 `PENDING`，人工确认后才允许新建替代记录。

字段命名映射：

| 数据库字段 | 协议/API 字段 | 说明 |
|---|---|---|
| `export_object.object_key` | `export_manifest.json.objects[].key`、`/api/objects/imported/check.objects[].key` | 数据库使用 `object_key` 避免和普通主键 `key` 混淆；协议和 API 使用 S3 原生命名 `key`。 |
| `object_ledger.source_key` | `export_manifest.json.objects[].key`、`/api/objects/imported/check.results[].key` | 中控账本使用 `source_key` 强调来源对象 key。 |
| `local_object_snapshot.metadata_json` | `export_manifest.json.objects[].metadata` | 扫描结果入库时用 JSON 字段；写 manifest 时输出为 `metadata`。 |
| `export_object.encryption_alg` | `disk_info.json.security.encryption_alg`、manifest `encryption_alg`、API `encryption_alg` | 数据加密算法命名保持一致。 |

### 4.4 disk_runtime

表用途：记录边缘端当前识别到的运输盘运行状态，用于热插拔、任务调度和前端展示。

| 字段名 | 类型 | 是否必填 | 字段说明 | 备注/约束 |
|---|---|---|---|---|
| `id` | bigint | 是 | 数据库主键 | 使用自增 bigint。 |
| `sn` | varchar | 是 | 运输盘硬件序列号 | 插盘后从 Linux 设备信息读取。 |
| `disk_id` | varchar/uuid | 否 | 运输盘逻辑 ID | 从 `disk_info.json` 或中控接口获取。 |
| `device_path` | varchar | 是 | Linux 设备路径 | 例如 `/dev/sdb`。 |
| `mount_path` | varchar | 否 | 挂载路径 | 例如 `/mnt/rustfs-transfer/disk-xxx`。 |
| `capacity_bytes` | bigint | 是 | 当前识别到的硬盘总容量 | 用于边缘端当前容量检测、任务编排和前端展示；可与 `disk_list.capacity_bytes` 做容量变化提示。 |
| `free_bytes` | bigint | 是 | 当前文件系统剩余容量 | 用于多盘任务编排和 WebSocket 展示。 |
| `reserve_bytes` | bigint | 是 | 当前预留容量 | 按协议公式 `max(1 GiB, min(8 GiB, free_bytes * 2%))` 计算，用于协议文件、元数据、日志、加密开销和安全余量。 |
| `object_budget_bytes` | bigint | 是 | 当前对象可分配容量 | `free_bytes - reserve_bytes - estimated_manifest_bytes - estimated_metadata_bytes - estimated_log_bytes - encryption_overhead_bytes`；调度对象或分块时只能使用该容量。 |
| `status` | varchar | 是 | 运行状态 | `DETECTED` 表示已检测到硬盘；`CHECKING` 表示校验中；`READY` 表示可用；`COPYING` 表示拷贝中；`CLEANING` 表示中控端正在清理已导入封存数据；`REINITIALIZING` 表示中控端正在重新初始化运输盘；`DONE` 表示任务完成；`REJECTED` 表示已拒绝使用；`REMOVED` 表示已拔出；`ERROR` 表示异常。 |
| `last_error_code` | varchar | 否 | 最近一次盘级错误码 | 例如 `DISK_REMOVED`、`RECOVERY_REQUIRED`、`FILESYSTEM_UNSUPPORTED`、`PROTOCOL_VERSION_UNSUPPORTED`、`MANIFEST_INVALID`、`CHECKSUM_MISMATCH`、`DECRYPT_FAILED`、`DISK_FULL`、`INSUFFICIENT_SPACE`、`PARTIAL_FILE_FOUND`、`PARTIAL_CLEAN_FAILED`、`REINIT_FAILED`。 |
| `error_message` | text | 否 | 最近一次盘级错误信息 | 用于生成 `disk_info.json.status.last_error` 和 WebSocket 展示；任务级错误仍写 `export_job.error_message` 或 `import_job.error_message`。 |
| `partial_residue_count` | integer | 是 | `.partial` 残留文件数量 | 默认 0；恢复扫描时统计。 |
| `partial_residue_bytes` | bigint | 是 | `.partial` 残留文件总字节数 | 默认 0；用于判断空间释放和前端提示。 |
| `last_seen_at` | timestamp | 是 | 最近一次检测到该盘的时间 | 热插拔监控更新，保存 UTC 时间。 |

`last_error_code` 常用盘级错误码中文含义：

| 错误码 | 中文含义 | 典型写入场景 |
|---|---|---|
| `DISK_REMOVED` | 运输盘已拔出 | 导出、导入、清理或重新初始化过程中检测到设备移除。 |
| `RECOVERY_REQUIRED` | 需要恢复检查 | 重插后发现盘内状态、任务账本、manifest 或 `.partial` 残留存在中间态。 |
| `FILESYSTEM_UNSUPPORTED` | 文件系统不支持 | 当前物理盘运行时检测到的文件系统不是 `ext4`，或挂载参数不满足要求。 |
| `PROTOCOL_VERSION_UNSUPPORTED` | 协议版本不兼容 | `disk_info.json.protocol.version` 与当前程序不兼容，或缺少当前版本必需字段。 |
| `MANIFEST_INVALID` | 清单非法 | manifest 缺失、JSON 解析失败、必填字段缺失、字段类型非法、`seal_id` 不一致或分块字段不连续。 |
| `CHECKSUM_MISMATCH` | 校验值不匹配 | manifest SHA256、密文 SHA256、明文 SHA256 或分块校验值与记录不一致。 |
| `DECRYPT_FAILED` | 解密失败 | 找不到可用于历史导入的密钥，或 AES-GCM tag 验证失败、解密失败。 |
| `DISK_FULL` | 写盘过程中磁盘满 | 写 `.partial`、metadata、manifest、日志或协议文件时底层返回 `ENOSPC`。 |
| `INSUFFICIENT_SPACE` | 可分配空间不足 | 按实时剩余空间和预留开销计算后，当前盘不能继续分配对象或分块。 |
| `PARTIAL_FILE_FOUND` | 发现未完成临时文件 | 恢复扫描时发现 `.partial` 残留。 |
| `PARTIAL_CLEANED` | 已清理临时残留 | `.partial` 残留已成功删除或隔离。 |
| `PARTIAL_CLEAN_FAILED` | 临时残留清理失败 | `.partial` 删除和隔离均失败，空间无法确认释放。 |
| `ORPHAN_EDGE_COPYING` | 边缘拷贝任务丢失 | 盘内残留 `EDGE_COPYING`，但边缘端找不到匹配的本地 `export_job`。 |
| `ORPHAN_CENTER_IMPORTING` | 中控导入任务丢失 | 盘内残留 `CENTER_IMPORTING`，但中控端找不到匹配的活动 `import_job`。 |
| `REINIT_FAILED` | 清理或重新初始化失败 | 导入完成后清理封存数据、创建目录结构、生成新密钥、写入或 `fsync` 新 `disk_info.json` 失败。 |

关键约束：

- `disk_runtime` 保存盘级运行状态、容量检测结果和低频 checkpoint；多盘并行拷贝时，WebSocket 的 `disks[]` 高频进度必须来自内存 `ProgressAggregator`，不得每秒扫描 `disk_runtime` 和 `export_object` 生成实时进度。
- 状态为 `REJECTED`（已拒绝使用）或 `ERROR`（异常）的运输盘不得进入拷贝任务池。
- `disk_runtime.status` 序列化到 WebSocket 时必须命名为 `runtime_status`，不得使用裸 `status`。
- 物理盘运行时检测文件系统不是 `ext4` 时，必须写入 `REJECTED` 和 `FILESYSTEM_UNSUPPORTED`。
- `disk_info.json.protocol.version` 不兼容或缺少当前版本必需字段时，必须写入 `REJECTED` 和 `PROTOCOL_VERSION_UNSUPPORTED`。
- 硬盘拔出后，必须写入 `REMOVED` 和 `DISK_REMOVED`；不得直接删除记录。
- 重新插入运输盘时，如果盘内 `disk_info.json.status.code` 残留为 `EDGE_COPYING` 或 `CENTER_IMPORTING`，必须先写入 `CHECKING` 和 `RECOVERY_REQUIRED` 并执行恢复判定；恢复判定失败时写入 `ERROR`，`last_error_code` / `error_message` 必须包含 `ORPHAN_EDGE_COPYING`、`ORPHAN_CENTER_IMPORTING`、`PARTIAL_FILE_FOUND` 等可定位错误码。
- 存在 `.partial` 临时文件时，不得把该盘直接置为 `READY` 或 `DONE`；必须先统计 `partial_residue_count`、`partial_residue_bytes`，再完成删除或隔离。
- `.partial` 删除或隔离成功后必须记录 `PARTIAL_CLEANED`，重新计算 `free_bytes`、`reserve_bytes`、`object_budget_bytes`，并把残留计数清零；删除和隔离均失败时必须写入 `ERROR` 和 `PARTIAL_CLEAN_FAILED`。
- `INSUFFICIENT_SPACE` 只表示该盘停止继续分配新对象，不表示已完成对象损坏；只有 `.partial` 清理失败、manifest/协议文件无法写入或 `fsync` 失败时，才进入盘级 `ERROR`。
- `CLEANING` 和 `REINITIALIZING` 只能用于 `disk_runtime.status`，不得写入盘内 `disk_info.json.status.code`。
- 导入完成后的清理或重新初始化失败时，`import_job.status = DONE` 不得回滚，盘内 `disk_info.json.status.code` 必须保持 `IMPORTED`，`disk_runtime.status = ERROR`，`last_error_code = REINIT_FAILED`。
- 重新初始化失败时，新生成但尚未完整写入盘内并完成签名/`fsync` 的 `data_key_id + disk_data_key` 不得置为可发放状态，不得返回给边缘端；下一次重试必须重新生成新的密钥对。
- 旧 `data_key.status` 只有在重新初始化全部成功后才允许更新为 `RETIRED`；如果清理或重新初始化失败，旧密钥状态保持可用于中控端历史校验和人工恢复的状态。
- `REINIT_FAILED` 状态下只允许中控端继续清理或重新初始化；不得再次导入同一 `disk_id + seal_id` 封盘批次，不得交付边缘端写入。
