# RustFS 离线运输盘同步开发契约

本文档用于约束边缘端、中控端、前端并行开发时的协议边界，避免出现两端状态、字段、通信方式对不上。

配套文档：

- [需求文档.md](需求文档.md)
- [数据库设计.md](数据库设计.md)
- [技术架构与技术选型.md](技术架构与技术选型.md)

## 1. 总体协作方式

本项目是双端程序通过运输盘协议协同工作。

```text
边缘端程序
  -> 通过 S3 API 读取边缘 RustFS
  -> 按运输盘协议写入硬盘
  -> 封盘

运输硬盘
  -> 携带 disk_info.json
  -> 携带 export_manifest.json
  -> 携带 data/ 对象数据
  -> 携带 meta/ 对象元数据

中控端程序
  -> 按运输盘协议读取硬盘
  -> 校验清单和对象
  -> 导入中控 RustFS
  -> 标记硬盘已导入
```

核心结论：

- 边缘端和中控端不是通过 WebSocket 同步数据。
- WebSocket 只负责后端程序向前端页面推送实时状态。
- 边缘端和中控端之间的在线交互使用 HTTP API。
- 离线数据交接使用运输盘上的协议文件。
- 中控端数据库是运输盘注册启用状态、边缘端注册信息和导入账本的权威库。
- 边缘端数据库是本地运行账本。

## 2. 通信边界

### 2.1 WebSocket 通信

WebSocket 只用于后端程序和前端页面之间的实时状态展示。

```text
边缘端后端程序 <-> 边缘端前端页面
中控端后端程序 <-> 中控端前端页面
```

WebSocket 不负责：

- 边缘端和中控端之间的数据同步。
- 运输盘状态的最终判定。
- 对象去重的最终判定。
- 文件内容传输。

WebSocket 负责展示：

- 硬盘插入和拔出。
- 硬盘注册状态。
- RustFS 扫描状态。
- 拷贝任务进度。
- 多运输盘并行拷贝时每块盘的独立进度。
- 当前正在拷贝的对象文件名。
- 当前对象剩余字节数。
- 当前运输盘剩余字节数。
- 当前任务总剩余字节数。
- 导入任务进度。
- 速度统计。
- 错误原因。
- 是否可拔盘。
- 是否可复用。

推送规则：

- 边缘端多盘并行拷贝时，必须至少每 1 秒推送一次 `COPY_PROGRESS`。
- 任意运输盘开始拷贝新对象时，必须立即推送一次 `COPY_PROGRESS`。
- 任意对象完成、失败、源对象变化或跳过时，必须立即推送一次 `COPY_PROGRESS`。
- 任意运输盘拔出、异常、空间不足或完成时，必须立即推送一次 `COPY_PROGRESS` 或 `ERROR`。
- `COPY_PROGRESS` 高频进度必须来自边缘端内存中的 `ProgressAggregator` 快照，由流式写入引擎在写 `.partial` 时实时更新。
- WebSocket Publisher 不得为了 1 秒推送而轮询或聚合 `export_job`、`export_object`、`disk_runtime`、`import_job` 或 `object_ledger`。
- 数据库只用于任务启动、恢复检查、页面首次加载、低频 checkpoint、对象状态变更、盘级状态变更和最终账本写入。
- `global_progress.remaining_bytes` 必须等于所有参与任务对象剩余字节数之和。
- 每个 `disks[].remaining_bytes` 必须等于该运输盘剩余待拷贝对象字节数之和。
- `current_object.remaining_bytes` 必须等于当前对象 `size_bytes - done_bytes`。
- 前端展示多盘进度时，必须以 `disks[]` 为每块盘的独立进度来源。

状态字段命名规则：

- WebSocket 和 HTTP API payload 不得使用裸 `status` 表示运输盘生命周期、运行态、任务态或对象态。
- 运输盘盘内生命周期必须命名为 `disk_status_code` 或 `status_code`，对应 `disk_info.json.status.code`。
- 运输盘运行态必须命名为 `runtime_status`，对应 `disk_runtime.status`。
- 导出任务状态必须命名为 `export_job_status`，对应 `export_job.status`。
- 导入任务状态必须命名为 `import_job_status`，对应 `import_job.status`。
- 统一事件中如使用 `job_status`，必须同时携带 `job_type`，并按 `job_type` 明确映射到 `export_job.status` 或 `import_job.status`。
- 对象状态必须命名为 `object_status`，对应 `export_object.status`。
- 边缘站点状态必须命名为 `edge_status`，对应 `edge_site.status`。
- 是否启用必须命名为 `disk_enabled` 或 `enabled`，对应 `disk_list.status`，不得与生命周期状态混用。
- 数据库表内部可以保留字段名 `status`，但跨表、跨进程、WebSocket、HTTP API 和 manifest 中必须带语义前缀。
- 例外：`disk_info.json` 作为盘内协议文件保留嵌套对象 `status.code`、`status.sealed`、`status.imported`、`status.reusable` 和 `status.last_error`；外部 API/WS 不得把该对象简化为裸 `status` 字符串。

### 2.2 HTTP API 通信

HTTP API 用于边缘端和中控端之间的在线校验。

```text
边缘端后端程序 -> 中控端后端程序
```

接口：

统一鉴权要求：

- 边缘端调用中控 HTTP API 必须携带鉴权信息，包括 `POST /api/edge/auth`。
- 鉴权信息必须放在 HTTP Header 中，不能放在 query string 中。
- 必填 Header：`X-Edge-Code`、`X-Auth-Key-Id`、`X-Timestamp`、`X-Nonce`、`X-Body-SHA256`、`X-Signature`。
- `X-Signature` 使用 `edge_auth_secret` 对规范化签名串做 HMAC-SHA256。
- `edge_auth_secret` 由中控端加密保存在 `edge_site.auth_secret_ciphertext`，边缘端部署注册后持有同一密钥；注册后禁止重置、替换或轮换。
- API 请求级 `nonce` 用于防重放，和 AES-GCM 加密对象使用的 `nonce` 不是同一个概念。
- 中控端必须拒绝时间偏差过大、签名错误、重复 nonce、边缘端禁用或密钥吊销的请求。

#### HTTP HMAC 签名规范

Header 规则：

| Header | 是否必填 | 说明 |
|---|---|---|
| `X-Edge-Code` | 是 | 边缘站点编码，对应 `edge_site.edge_code`。 |
| `X-Auth-Key-Id` | 是 | HTTP API 鉴权密钥编号，对应 `edge_site.auth_key_id`。 |
| `X-Timestamp` | 是 | 请求发起时间，ISO8601 UTC 格式，例如 `2026-08-08T12:00:00Z`。 |
| `X-Nonce` | 是 | API 请求级随机数，同一 `X-Auth-Key-Id + X-Nonce` 在有效窗口内只能使用一次。 |
| `X-Body-SHA256` | 是 | 原始 HTTP 请求体字节的 SHA256 摘要，使用 lowercase hex 编码；空请求体使用空字节摘要。 |
| `X-Signature` | 是 | Base64 编码的 HMAC-SHA256 签名。 |

签名串：

```text
string_to_sign =
  METHOD + "\n" +
  canonical_path_with_query + "\n" +
  X-Timestamp + "\n" +
  X-Nonce + "\n" +
  X-Body-SHA256
```

规范化规则：

- `METHOD` 必须使用 HTTP 方法大写值，例如 `GET`、`POST`。
- `canonical_path_with_query` 只包含 path 和 query，不包含 scheme、host、port 和 fragment。
- path 必须使用服务端收到的 URL path，保持 `/` 分隔；不得把空 path 当成其他值，空 path 规范化为 `/`。
- query 参数必须按参数名升序排序；同名参数按参数值升序排序。
- query 参数名和值必须使用 RFC 3986 percent-encoding；空 query 时 `canonical_path_with_query` 只包含 path，不追加 `?`。
- `X-Body-SHA256` 必须对原始 HTTP body bytes 计算，不能对重新序列化后的 JSON 计算。
- 中控端必须先通过 `X-Edge-Code` 查询 `edge_site`，确认 `edge_site.status = ACTIVE` 且 `X-Auth-Key-Id = edge_site.auth_key_id`，再解密 `edge_site.auth_secret_ciphertext` 得到 `edge_auth_secret`。
- `X-Signature = base64(HMAC-SHA256(edge_auth_secret, UTF-8 bytes of string_to_sign))`。
- Header 名大小写按 HTTP 语义不敏感，但签名串中的 Header 值必须使用请求实际值去除首尾空白后的结果。
- 如果请求体中也包含 `edge_code`，其值必须与 `X-Edge-Code` 完全一致；不一致时必须拒绝请求，HTTP 状态码为 `400 Bad Request`，错误码为 `INVALID_REQUEST`。

防重放规则：

- 中控端允许的 `X-Timestamp` 时间偏差最大为 300 秒。
- 中控端必须在进程内按 `X-Auth-Key-Id + X-Nonce` 维护已使用 nonce 的 TTL 缓存，保存时间不得少于 10 分钟，不新增数据库表。
- 同一 `X-Auth-Key-Id + X-Nonce` 在保存窗口内重复出现时，必须拒绝请求。
- 中控端重启会清空进程内 nonce 缓存；重启后仍必须执行 `X-Timestamp` 时间窗口校验。
- 验签、时间窗口、nonce 去重、边缘端状态和密钥状态任一检查失败时，HTTP 状态码必须为 `401 Unauthorized`，错误码为 `UNAUTHORIZED`；服务端日志必须记录 `request_id`、`edge_code`、`auth_key_id` 和拒绝原因。

#### POST /api/edge/auth

用途：边缘端启动或部署后校验站点身份，确认该边缘端是否允许接入中控端。

鉴权：必须使用上面的 HTTP HMAC 签名规范。该接口用于确认边缘端是否允许接入，不是免签接口。

请求体：

| 字段名 | 类型 | 是否必填 | 字段说明 | 备注/约束 |
|---|---|---|---|---|
| `client_version` | string | 否 | 边缘端程序版本 | 用于兼容性排查和审计。 |

响应体：

| 字段名 | 类型 | 是否必填 | 字段说明 | 备注/约束 |
|---|---|---|---|---|
| `allowed` | boolean | 是 | 是否允许接入 | `false` 时边缘端不得继续调用导出相关接口。 |
| `edge_code` | string | 是 | 边缘站点编码 | 中控端确认后的站点编码。 |
| `edge_name` | string | 是 | 边缘站点名称 | 前端展示用。 |
| `edge_status` | string | 是 | 边缘站点状态 | 来自 `edge_site.status`；`ACTIVE`、`DISABLED` 或 `ERROR`。不得使用裸 `status`。 |
| `server_time` | string | 是 | 中控端当前时间 | ISO8601 格式，用于排查时间偏差。 |
| `message` | string | 否 | 说明信息 | 拒绝时写明原因。 |

#### POST /api/disk/verify

用途：边缘端插入运输盘后，向中控端校验该盘是否注册、启用、状态是否允许导出。

请求体：

| 字段名 | 类型 | 是否必填 | 字段说明 | 备注/约束 |
|---|---|---|---|---|
| `edge_code` | string | 是 | 边缘站点编码 | 用于判断边缘端是否有权限使用该盘。 |
| `disk_id` | string | 是 | 运输盘逻辑 ID | 来自 `disk_info.json.disk.disk_id`。 |
| `sn` | string | 否 | 硬盘硬件序列号 | SN 可能为空或不稳定，只做辅助校验。 |
| `capacity_bytes` | number | 是 | 当前识别到的硬盘总容量 | 用于容量异常提示。 |
| `free_bytes` | number | 是 | 当前文件系统剩余空间 | 用于中控端辅助判断。 |
| `status_code` | string | 是 | 盘内生命周期状态 | 来自 `disk_info.json.status.code`。 |
| `protocol_version` | string | 是 | 运输盘协议版本 | 来自 `disk_info.json.protocol.version`。 |

响应体：

| 字段名 | 类型 | 是否必填 | 字段说明 | 备注/约束 |
|---|---|---|---|---|
| `allowed` | boolean | 是 | 是否允许边缘端使用该盘 | `false` 时必须拒绝导出和写入。 |
| `disk_id` | string | 是 | 运输盘逻辑 ID | 中控端确认后的 `disk_id`。 |
| `disk_enabled` | boolean | 是 | 运输盘是否启用 | 来自中控端 `disk_list.status`。 |
| `expected_status` | string | 是 | 期望盘内状态 | 边缘端导出前通常应为 `INITIALIZED`。 |
| `action` | string | 是 | 动作 | `ALLOW_EXPORT`、`REJECT`、`NEED_INIT`、`NEED_IMPORT_FIRST`。 |
| `message` | string | 否 | 说明信息 | 拒绝时写明原因。 |

命名规则：

- `status_code` 只表示运输盘盘内生命周期状态，等同于 `disk_info.json.status.code`。
- `disk_enabled` 只表示中控注册表启用状态，来自 `disk_list.status`。
- `expected_status` 只表示中控端期望边缘端看到的盘内生命周期状态，通常为 `INITIALIZED`。
- API 不得用裸 `status` 表示运输盘生命周期、站点状态、任务状态或运行状态，避免与 `disk_list.status`、`edge_site.status`、任务状态、运行状态混淆。

#### POST /api/disk/export-key

用途：边缘端通过校验后，向中控端领取当前运输盘的数据加密密钥，用于 AES-256-GCM 加密写盘。

请求体：

| 字段名 | 类型 | 是否必填 | 字段说明 | 备注/约束 |
|---|---|---|---|---|
| `edge_code` | string | 是 | 边缘站点编码 | 必须为已启用边缘端。 |
| `disk_id` | string | 是 | 运输盘逻辑 ID | 必须是已注册且启用的运输盘。 |
| `data_key_id` | string | 是 | 数据加密密钥编号 | 来自 `disk_info.json.security.data_key_id`。 |
| `export_job_id` | string | 是 | 边缘端导出任务 ID | 中控端记录到 `data_key.export_job_id`，用于审计。 |
| `status_code` | string | 是 | 当前盘内状态 | 必须为 `INITIALIZED` 或边缘端准备写入前的允许状态。 |

响应体：

| 字段名 | 类型 | 是否必填 | 字段说明 | 备注/约束 |
|---|---|---|---|---|
| `allowed` | boolean | 是 | 是否允许领取密钥 | `false` 时边缘端不得开始导出。 |
| `data_key_id` | string | 是 | 数据加密密钥编号 | 与请求一致。 |
| `encryption_alg` | string | 是 | 加密算法 | 固定为 `AES-256-GCM`。 |
| `disk_data_key` | string | 条件必填 | 明文数据加密密钥 | 仅 `allowed = true` 时返回；Base64 编码；边缘端只能内存使用，不得落库或写盘。 |
| `message` | string | 否 | 说明信息 | 拒绝时写明原因。 |

密钥生命周期规则：

- `disk_data_key` 不设置时间过期字段；`/api/disk/export-key` 不返回 `expires_at`。
- `disk_data_key` 的有效性跟随运输盘和封盘批次生命周期，不跟随时钟时间。
- 边缘端第一次领取成功后，只要该盘仍处于本次导出生命周期内，即使中控端后续不可达，也可以继续完成本次导出。
- 运输盘封盘为 `SEALED` 后，中控端不得再向边缘端发放该 `data_key_id` 对应的 `disk_data_key` 用于继续写入。
- 中控端导入完成并重新初始化运输盘后，旧 `data_key_id` 必须作废，不得再发放给任何边缘端；重新初始化必须生成新的 `data_key_id + disk_data_key`。

#### GET /api/disk/{disk_id}

用途：边缘端查询运输盘注册信息和是否启用。运输盘生命周期状态以盘内 `disk_info.json.status.code` 为准。

响应体：

| 字段名 | 类型 | 是否必填 | 字段说明 | 备注/约束 |
|---|---|---|---|---|
| `disk_id` | string | 是 | 运输盘逻辑 ID | 中控端登记的稳定 ID。 |
| `sn` | string | 否 | 硬盘硬件序列号 | 仅辅助展示和校验。 |
| `enabled` | boolean | 是 | 是否启用 | `false` 时边缘端不得使用。 |
| `last_init_time` | string | 否 | 最近初始化时间 | ISO8601 格式。 |
| `remark` | string | 否 | 备注 | 前端展示用。 |

#### POST /api/objects/imported/check

用途：边缘端批量查询对象是否已被中控导入，用于导出前去重优化。该接口只是只读、按需、增量查询优化，最终去重仍以中控导入时写 `object_ledger` 为准；查询结果不得回写为 `export_object.status`。

边界规则：

- 边缘端本地 `export_object.status` 不保存中控导入结果。
- 中控是否已入库只由中控端 `object_ledger` 和 `import_job` 判断。
- 该接口返回的 `results[].imported` 只能用于本次扫描/调度时的跳过决策或前端提示，不得把边缘端对象状态改成 `IMPORTED`。

请求体：

| 字段名 | 类型 | 是否必填 | 字段说明 | 备注/约束 |
|---|---|---|---|---|
| `edge_code` | string | 是 | 边缘站点编码 | 区分不同边缘端来源。 |
| `objects` | array | 是 | 待查询对象列表 | 单次必须限制数量，避免请求过大。 |
| `objects[].bucket` | string | 是 | 源 bucket | 来自边缘 RustFS。 |
| `objects[].key` | string | 是 | 源 object key | 来自边缘 RustFS。 |
| `objects[].etag` | string | 是 | 源对象 ETag | 用于识别对象版本。 |
| `objects[].size_bytes` | number | 是 | 源对象大小 | 用于识别对象版本。 |
| `objects[].last_modified` | string | 是 | 源对象最后修改时间 | 用于识别同名覆盖对象。 |

响应体：

| 字段名 | 类型 | 是否必填 | 字段说明 | 备注/约束 |
|---|---|---|---|---|
| `results` | array | 是 | 查询结果列表 | 与请求对象逐条对应。 |
| `results[].bucket` | string | 是 | 源 bucket | 原样返回。 |
| `results[].key` | string | 是 | 源 object key | 原样返回。 |
| `results[].imported` | boolean | 是 | 是否已导入 | `true` 表示中控账本已有匹配记录。 |
| `results[].imported_at` | string | 否 | 导入完成时间 | 已导入时返回。 |
| `results[].import_bucket` | string | 否 | 中控归档 bucket | 已导入时返回。 |
| `results[].import_key` | string | 否 | 中控归档 key | 已导入时返回。 |

统一错误响应：

| 字段名 | 类型 | 是否必填 | 字段说明 | 备注/约束 |
|---|---|---|---|---|
| `error_code` | string | 是 | 错误码 | 例如 `UNAUTHORIZED`、`DISK_NOT_FOUND`、`DISK_DISABLED`、`INVALID_STATUS`、`KEY_REVOKED`、`NONCE_REUSED`。 |
| `message` | string | 是 | 错误说明 | 给前端或日志展示。 |
| `request_id` | string | 是 | 请求 ID | 用于日志追踪。 |

HTTP 状态码规则：

| HTTP 状态码 | 使用场景 |
|---|---|
| `200 OK` | 请求成功，业务是否允许继续由响应体 `allowed` 或 `results` 判断。 |
| `400 Bad Request` | 请求 JSON 无法解析、字段类型错误、缺少业务必填字段或字段格式不合法。 |
| `401 Unauthorized` | HTTP HMAC 鉴权失败、时间偏差过大、请求 nonce 重复、边缘端禁用或鉴权密钥吊销。 |
| `403 Forbidden` | 鉴权通过，但该边缘端或运输盘没有执行当前动作的权限。 |
| `404 Not Found` | 请求中的 `disk_id`、`data_key_id` 或其他资源不存在。 |
| `409 Conflict` | 状态冲突、重复导入、封盘批次冲突、nonce 重复或幂等冲突。 |
| `500 Internal Server Error` | 中控端内部错误、数据库错误或非预期异常。 |

标准错误码：

| 错误码 | 中文名称 | 触发条件 |
|---|---|---|
| `UNAUTHORIZED` | 未授权 | 缺少鉴权信息、签名错误、时间偏差过大、请求 nonce 重复或边缘端未通过认证。 |
| `INVALID_REQUEST` | 请求格式错误 | 请求体无法解析、必填字段缺失、字段类型不正确，或请求体 `edge_code` 与 Header `X-Edge-Code` 不一致。 |
| `DISK_NOT_FOUND` | 运输盘不存在 | 中控端找不到请求中的 `disk_id`，或 `disk_id` 与注册信息不匹配。 |
| `DISK_DISABLED` | 运输盘已禁用 | `disk_list.status = false`，该盘不得被边缘端导出或清理。 |
| `DISK_REMOVED` | 运输盘已拔出 | 导出、导入、清理或重新初始化过程中检测到设备移除，当前任务必须中断并等待重插恢复。 |
| `INVALID_STATUS` | 状态不允许 | 盘内 `disk_info.json.status.code` 不符合当前接口或当前端允许处理的状态。 |
| `RECOVERY_REQUIRED` | 需要恢复检查 | 重插后发现盘内状态、任务账本、manifest 或 `.partial` 残留存在中间态，必须先进入恢复判定。 |
| `PROTOCOL_VERSION_UNSUPPORTED` | 协议版本不兼容 | `disk_info.json.protocol.version` 高于当前程序支持版本、major version 不兼容，或缺少当前版本必需协议字段。 |
| `FILESYSTEM_UNSUPPORTED` | 文件系统不支持 | 当前物理盘运行时检测到的文件系统不是 `ext4`，或挂载参数不满足写盘/导入要求。 |
| `KEY_REVOKED` | 密钥已吊销 | 请求使用的签名密钥或 `data_key_id` 已被吊销，不得继续发放或使用；边缘端 HTTP 鉴权禁用通过 `edge_site.status = DISABLED` 表达。 |
| `SIGNATURE_INVALID` | 协议签名无效 | `disk_info.json` 的 `center_signature` 验签失败，或签名覆盖字段、规范化方式不符合协议要求。 |
| `MANIFEST_INVALID` | 清单非法 | manifest 缺失、JSON 解析失败、必填字段缺失、字段类型非法、顶层 `seal_id` 与 `disk_info.json.edge.seal_id` 不一致，或分块字段不连续。 |
| `CHECKSUM_MISMATCH` | 校验值不匹配 | manifest SHA256、密文 SHA256、明文 SHA256 或分块校验值与文档记录不一致。 |
| `DECRYPT_FAILED` | 解密失败 | 中控端按 `data_key_id` 找不到可用于历史导入的密钥，或 AES-GCM tag 验证失败、解密失败。 |
| `NONCE_REUSED` | AES-GCM nonce 重复 | 同一 `data_key_id` 下发现重复 AES-GCM nonce；可能发生在 manifest 内部重复，或与历史 `object_ledger` 记录重复。 |
| `SOURCE_CHANGED` | 源对象变化 | 边缘端下载前后 HEAD 结果不一致，说明源对象上传、覆盖或 metadata 变化；该对象不得进入有效 manifest。 |
| `CHUNK_INDEX_OVERFLOW` | 分块数量超限 | 单对象按 `10 GiB` 分块后 `chunk_total` 超过 `1,000,000`，或 `chunk_index`、`chunk_total` 超出协议允许范围。 |
| `SEAL_ID_MANIFEST_MISMATCH` | 封盘批次与清单不匹配 | 同一 `disk_id + seal_id` 已存在导入任务，但本次读取到的 `manifest_sha256` 与历史记录不一致。 |
| `ORPHAN_EDGE_COPYING` | 边缘拷贝任务丢失 | 盘内残留 `EDGE_COPYING`，但边缘端找不到匹配的本地 `export_job`，无法自动恢复。 |
| `ORPHAN_CENTER_IMPORTING` | 中控导入任务丢失 | 盘内残留 `CENTER_IMPORTING`，但中控端找不到匹配 `disk_id + seal_id` 的活动 `import_job`，无法自动恢复。 |
| `PARTIAL_FILE_FOUND` | 发现未完成临时文件 | 恢复扫描时发现 `.partial` 文件；该文件不得进入 manifest 或导入流程。 |
| `PARTIAL_CLEANED` | 已清理临时残留 | 恢复扫描时发现 `.partial` 文件并已成功删除。 |
| `PARTIAL_CLEAN_FAILED` | 临时残留清理失败 | `.partial` 文件删除和隔离均失败，空间无法确认释放，必须进入盘级 `ERROR` 等待人工处理。 |
| `INSUFFICIENT_SPACE` | 可分配空间不足 | 分配前按实时剩余空间和预留开销计算后，`object_budget_bytes <= 0` 或不足以容纳下一个对象/分块。 |
| `DISK_FULL` | 写盘过程中磁盘满 | 写 `.partial`、metadata、manifest、日志或协议文件时底层返回 `ENOSPC` / no space left on device。 |
| `REINIT_FAILED` | 清理或重新初始化失败 | 导入已完成后，清理封存数据、创建目录结构、生成新密钥、写入或 `fsync` 新 `disk_info.json` 失败。 |

接口原则：

- 边缘端不得通过 API 修改中控端导入状态。
- 边缘端不得通过 API 将运输盘标记为 `IMPORTED`。
- 清理封存数据和重新初始化只能由中控端执行；边缘端不得通过 API 或本地流程清理运输盘。
- 中控端不可达但边缘端已完成硬盘校验并已领取本次 `disk_data_key` 时，边缘端可以继续基于本地账本导出；该密钥不按时间过期。如果尚未领取数据加密密钥，则不得开始新的加密导出；运输盘进入 `SEALED` 后不得再领取同一 `data_key_id` 用于继续写入。

### 2.3 运输盘协议通信

运输盘协议用于边缘端和中控端的离线交接。

```text
运输硬盘
  /rustfs-transfer/disk_info.json
  /rustfs-transfer/manifests/export_manifest.json
  /rustfs-transfer/manifests/export_manifest.sha256
  /rustfs-transfer/data/
  /rustfs-transfer/meta/
  /rustfs-transfer/logs/
  /rustfs-transfer/quarantine/partial/
```

边缘端负责按协议写盘和封盘。

中控端负责按协议验盘和导入。

协议路径规则：

- `/rustfs-transfer/` 是运输盘协议根目录；所有协议路径均以该目录为根。
- `disk_info.json` 固定路径为 `/rustfs-transfer/disk_info.json`。
- manifest 固定路径为 `/rustfs-transfer/manifests/export_manifest.json`。
- manifest SHA256 固定路径为 `/rustfs-transfer/manifests/export_manifest.sha256`。
- 对象密文或密文分块固定写入 `/rustfs-transfer/data/`。
- 对象 metadata sidecar 固定写入 `/rustfs-transfer/meta/`。
- 导出和导入日志摘要固定写入 `/rustfs-transfer/logs/`。
- 无法删除的 `.partial` 残留固定隔离到 `/rustfs-transfer/quarantine/partial/`。
- `disk_info.json.manifest.manifest_path`、manifest `objects[].relative_data_path`、manifest `objects[].relative_meta_path` 必须是相对于 `/rustfs-transfer/` 的相对路径，不得以 `/` 开头，不得包含 `..`，不得越过协议根目录。
- 中控端导入时不得猜测路径；必须按 `disk_info.json.manifest.manifest_path`、`disk_info.json.manifest.manifest_sha256_path` 和 manifest 内 `relative_*_path` 读取。路径不存在、越界、指向目录或与固定目录规范不符时，必须拒绝导入，错误码 `MANIFEST_INVALID`。

容量编排必须按对象可用容量计算，不能直接使用硬盘总容量。

```text
reserve_bytes = max(1 GiB, min(8 GiB, free_bytes * 2%))
object_budget_bytes = free_bytes
                    - reserve_bytes
                    - estimated_manifest_bytes
                    - estimated_metadata_bytes
                    - estimated_log_bytes
                    - encryption_overhead_bytes
```

`reserve_bytes` 用于：

- `disk_info.json`、manifest、manifest 校验文件。
- `meta/` 对象元数据 sidecar。
- `logs/` 导出和导入日志。
- AES-256 加密文件头、nonce、tag、padding 或分块索引等额外开销。
- `.partial` 临时文件、文件系统块对齐和容量统计误差。

规则：

- 对象或分块分配前，必须使用实时 `free_bytes` 重新计算 `object_budget_bytes`。
- 分配对象时必须使用预计落盘大小，而不是只使用源对象 `size_bytes`。
- 预计落盘大小必须包含加密开销和 metadata 开销。
- 如果 `object_budget_bytes <= 0` 或不足以容纳下一个对象/分块，当前运输盘不得继续分配新对象，必须记录错误码 `INSUFFICIENT_SPACE` 并重新计算 `disk_runtime.free_bytes`。
- 空间不足不等于整盘损坏：如果该盘已有 `EXPORTED` 对象，可以停止接收新对象并进入封盘前校验；如果没有任何 `EXPORTED` 对象，应保持 `INITIALIZED` 或标记当前任务失败，等待重新分配。
- 边缘端必须直接流式加密写入 `.partial`，成功后重命名为最终密文文件，避免同一对象同时占用明文临时文件和密文最终文件两份空间。

示例：

| 当前剩余空间 | 预留空间 | 可分配对象数据容量 |
|---|---:|---:|
| 1 TiB | 8 GiB | 1016 GiB |
| 4 TiB | 8 GiB | 4088 GiB |
| 8 TiB | 8 GiB | 8184 GiB |

## 3. 运输盘状态机

运输盘状态只能使用以下枚举。所有状态必须按表格含义实现，不能只按中文名称自行理解。

| 状态码 | 中文名称 | 状态含义 | 主要写入方 | 允许动作 | 禁止动作 | 下一步状态 |
|---|---|---|---|---|---|---|
| `UNREGISTERED` | 未注册 | 中控数据库中不存在该硬盘 SN 或 `disk_id`，该盘不属于系统授权运输盘。该状态通常不写入 `disk_info.json`，由程序识别后展示。 | 中控端判断 | 前端提示未注册；中控端可人工注册。 | 边缘端清盘；边缘端拷贝；中控端导入。 | `REGISTERED` |
| `REGISTERED` | 已注册 | 中控数据库已登记该硬盘 SN 和 `disk_id`，但运输盘尚未初始化或尚未写入有效协议文件。 | 中控端 | 中控端初始化、格式化、写入 `disk_info.json`。 | 边缘端直接使用；中控端导入。 | `INITIALIZED` |
| `INITIALIZED` | 已初始化 | 运输盘已由中控端初始化，协议文件有效，当前没有封存数据，可交付边缘端写入。 | 中控端 | 边缘端校验通过后开始拷贝；中控端重新初始化。 | 中控端导入；边缘端当作已封盘数据处理。 | `EDGE_COPYING` |
| `EDGE_COPYING` | 边缘拷贝中 | 边缘端正在向运输盘写入对象数据、元数据和清单。此状态下运输盘不可拔出、不可导入、不可清理。 | 边缘端 | 边缘端继续拷贝；边缘端失败后标记异常。 | 中控端导入；边缘端清盘；人工拔盘。 | `SEALED` 或 `ERROR` |
| `SEALED` | 已封盘待导入 | 边缘端已完成对象写入、manifest 生成、校验值计算和封盘。该盘只允许中控端读取并导入。 | 边缘端 | 中控端校验并导入；中控端失败后标记异常。 | 边缘端继续写入；边缘端清盘；重复封盘。 | `CENTER_IMPORTING` 或 `ERROR` |
| `CENTER_IMPORTING` | 中控导入中 | 中控端正在读取运输盘并导入中控 RustFS。此状态下运输盘不可拔出、不可清理。 | 中控端 | 中控端继续校验、上传、写入导入账本。 | 边缘端写入；边缘端清盘；人工拔盘。 | `IMPORTED` 或 `ERROR` |
| `IMPORTED` | 已导入待复用 | 中控端已完成 manifest 内全部有效对象的校验、去重、导入和账本写入。该盘只表示允许中控端进入清理和重新初始化流程，不能直接交付边缘端写入。 | 中控端 | 中控端清理封存数据并重新初始化。 | 边缘端清盘；边缘端重新初始化；再次按封盘数据导入；边缘端不经重新初始化直接写入。 | `INITIALIZED` |
| `ERROR` | 异常 | 当前运输盘或任务发生错误，需要根据错误来源决定恢复方式。此状态默认不可复用。 | 边缘端或中控端 | 前端展示错误；人工确认；按错误类型重置。 | 自动清理未导入封盘数据；自动标记已导入。 | `INITIALIZED` 或保持 `ERROR` |

正常流转：

```text
UNREGISTERED
-> REGISTERED
-> INITIALIZED
-> EDGE_COPYING
-> SEALED
-> CENTER_IMPORTING
-> IMPORTED
-> INITIALIZED
```

异常流转：

```text
EDGE_COPYING -> ERROR
CENTER_IMPORTING -> ERROR
ERROR -> INITIALIZED
```

判断规则：

- 程序判断主状态只能使用 `status.code`。
- `sealed`、`imported`、`reusable` 只作为展示冗余字段。
- 写入 `status.code` 时，必须同步推导冗余字段。

签名规范：

- `disk_info.json` 签名输入必须使用 RFC 8785 JSON Canonicalization Scheme 生成 `canonical_json`。
- 签名输入必须是 `canonical_json` 的 UTF-8 字节。
- 签名输出必须是 Base64 编码的 HMAC-SHA256 结果。
- 计算签名时，必须从签名输入中排除 `security.center_signature`，避免签名字段自引用。
- `center_signature` 覆盖字段：
  - `protocol`
  - `disk`
  - `center`
  - `security.center_key_id`
  - `security.signature_alg`
  - `security.data_key_id`
- `center_signature` 只证明中控端初始化和重新初始化时写入的中控基础字段、运输盘身份和密钥绑定未被篡改；边缘端写入的 `status`、`edge` 和 `manifest` 不由协议签名证明。
- 中控端导入 `SEALED` 运输盘时，不校验边缘签名；必须通过 `disk_id + data_key_id` 密钥绑定、manifest SHA256、路径约束、`data_key_id + nonce` 唯一性、AES-GCM tag、密文 SHA256 和明文 SHA256 校验来确认封盘数据可导入。
- 中控端写入 `IMPORTED` 或重新初始化为 `INITIALIZED` 后，必须重新计算并写入 `center_signature`。
- manifest 本身不单独保存签名；导入时必须用 `export_manifest.sha256` 和 `disk_info.json.manifest.manifest_sha256` 校验 manifest 内容一致，并继续校验每个对象或分块的 AES-GCM tag、密文 SHA256 和明文 SHA256。
- 验签失败时必须拒绝导出、导入、清理或重新初始化，错误码为 `SIGNATURE_INVALID`。

写文件规则：

- 每次写入 `disk_info.json` 必须先写临时文件。
- 临时文件校验成功后再原子重命名为 `disk_info.json`。
- 写入后必须 fsync，降低拔盘导致文件损坏的风险。

### 4.1 运输盘落盘加密流程

加密目标：运输盘离线运输过程中，即使硬盘丢失，也不能直接读取对象明文数据。

采用 AES-256-GCM 做对象数据落盘加密。

密钥职责：

- 中控端生成和保存数据加密密钥。
- 边缘端只在导出任务运行期间临时获取数据加密密钥。
- 运输盘上只保存 `data_key_id`、加密算法、nonce、tag、密文校验值等非敏感信息。
- 运输盘上禁止保存明文数据加密密钥。
- HTTP API 授权码不得复用为数据加密密钥。

流程：

```text
中控端初始化运输盘
-> 生成 data_key_id
-> 生成 256-bit disk_data_key
-> 中控端安全保存 data_key_id 与 disk_data_key，data_key.status = ACTIVE
-> disk_info.json 写入 encryption_alg = AES-256-GCM
-> disk_info.json 写入 data_key_id
-> 运输盘交付边缘端

边缘端插入运输盘
-> 使用 edge_auth_secret 调用中控端校验接口
-> 校验 disk_id、edge_code、status.code
-> 中控端确认允许导出后返回本次 data_key_id 对应的 disk_data_key
-> 中控端将 data_key.status 更新为 ISSUED，并绑定 edge_code 和 export_job_id
-> 边缘端只在内存中持有 disk_data_key
-> 边缘端流式读取 RustFS 对象
-> 使用 AES-256-GCM 加密写入 .partial
-> 写入完成后 fsync
-> 计算密文 SHA256
-> 记录 nonce、tag、ciphertext_sha256、ciphertext_size_bytes
-> 原子重命名为最终密文文件
-> 封盘后中控端只能把该 data_key 用于导入解密，不得再发放给边缘端写入
-> 导出完成后清理内存中的 disk_data_key

中控端导入运输盘
-> 读取 disk_info.json 中的 data_key_id
-> 从中控端密钥存储中读取 disk_data_key
-> 校验 manifest 和密文 SHA256
-> 使用 nonce、tag 和 disk_data_key 解密对象或分块
-> 解密后校验 plaintext_sha256
-> 解密成功后上传到中控 RustFS
-> 上传成功后写 object_ledger
-> 导入完成并重新初始化运输盘后，将旧 data_key.status 更新为 RETIRED
```

数据加密密钥状态机：

| 状态码 | 中文名称 | 允许发给边缘端导出 | 允许中控导入解密 | 状态含义 | 下一步状态 |
|---|---|---|---|---|---|
| `ACTIVE` | 已生成待领取 | 是 | 是 | 中控初始化运输盘后生成，尚未被边缘端领取或绑定导出任务。 | `ISSUED`、`REVOKED` |
| `ISSUED` | 已发放导出中 | 是，仅限已绑定的 `edge_code + export_job_id` | 是 | 边缘端已领取密钥，允许继续完成本次导出；中控不可达不影响已领取密钥完成本次导出。 | `SEALED_READONLY`、`REVOKED` |
| `SEALED_READONLY` | 已封盘只读 | 否 | 是 | 运输盘已封盘，密钥只能用于中控端导入解密，不得再发给边缘端继续写入。 | `RETIRED`、`REVOKED` |
| `RETIRED` | 已退役 | 否 | 是，仅限历史审计、重复插盘幂等校验或人工恢复 | 中控导入完成并重新初始化运输盘后，旧密钥退役；保留密钥记录，禁止物理删除。 | 保持 `RETIRED` |
| `REVOKED` | 已吊销 | 否 | 默认否，确需历史解密必须人工审批并审计 | 密钥疑似泄露或人工吊销，禁止继续发放；历史解密不自动允许。 | 保持 `REVOKED` |

状态流转规则：

- `ACTIVE` 或已绑定同一 `edge_code + export_job_id` 的 `ISSUED` 才允许 `/api/disk/export-key` 返回明文 `disk_data_key`。
- `SEALED_READONLY`、`RETIRED`、`REVOKED` 都不得通过 `/api/disk/export-key` 发放给边缘端。
- 边缘端封盘成功并写入 `SEALED` 后，中控端在下一次看到该盘或导入前，必须把对应 `data_key.status` 更新为 `SEALED_READONLY`，并把 `disk_info.json.edge.seal_id` 绑定到 `data_key.seal_id`。
- 中控端导入完成、写入 `IMPORTED` 并重新初始化运输盘后，必须把旧 `data_key.status` 更新为 `RETIRED`，并为新初始化盘生成新的 `data_key_id + disk_data_key`。
- `RETIRED` 密钥不得再用于新导出，但必须保留以支持历史审计、重复插盘幂等校验或人工恢复。

AES-256-GCM 规则：

- 每个对象或每个分块必须使用唯一 nonce。
- 同一个 `disk_data_key` 下禁止复用 nonce。
- nonce 必须使用 96-bit 随机值，Base64 或 Hex 编码后写入 manifest。
- 边缘端写入 `export_object` 时必须保证同一 `data_key_id + nonce` 唯一；如果生成重复 nonce，必须丢弃该 nonce 并重新生成，不得继续加密。
- tag 必须写入 manifest 或附加在密文文件末尾，但 manifest 中必须明确记录。
- 解密时必须先完成 GCM 认证校验，认证失败不得上传到中控 RustFS。
- 中控端导入前必须检查 manifest 内部是否存在重复 `data_key_id + nonce`；如果存在，必须拒绝导入并记录错误码 `NONCE_REUSED`。
- 中控端导入普通对象前必须查询 `object_ledger`，确认同一 `data_key_id + nonce` 没有被已导入普通对象使用；如果已使用，必须拒绝导入并记录错误码 `NONCE_REUSED`。
- 中控端登记跨盘分块前必须查询 `chunk_import_part` 和 `object_ledger`，确认同一 `data_key_id + nonce` 没有被其他分块或普通对象使用；如果已使用且不是同一分块的幂等重放，必须拒绝导入并记录错误码 `NONCE_REUSED`。
- AAD 必须绑定 `disk_id`、`seal_id`、`export_job_id`、`bucket`、`key`、`chunk_group_id`、`chunk_index`、`chunk_total`、`chunk_offset_bytes`，防止密文被跨盘、跨批次、跨对象或跨分块替换。

- 只允许记录完整导出成功的对象。
- manifest 顶层 `seal_id` 必须与 `disk_info.json.edge.seal_id` 一致；不一致时中控端必须拒绝导入。
- `.partial` 临时文件不得进入 manifest。
- `SOURCE_CHANGED`、`FAILED` 对象可以进入任务日志，但不得作为有效导入对象；对象下载前后 HEAD 结果不一致时，必须写入 `export_object.status = SOURCE_CHANGED` 和 `export_object.error_code = SOURCE_CHANGED`。
- `relative_data_path` 和 `relative_meta_path` 只用于定位运输盘文件，必须是相对于 `/rustfs-transfer/` 的相对路径。
- `relative_data_path` 必须位于 `data/` 下，`relative_meta_path` 必须位于 `meta/` 下；两者不得以 `/` 开头，不得包含 `..`，不得指向 `quarantine/`、`logs/`、`manifests/` 或协议根目录外文件。
- 中控端解析路径时必须先规范化再校验仍位于 `/rustfs-transfer/` 下；校验失败时拒绝导入，错误码 `MANIFEST_INVALID`。
- 运输盘上 `data/` 目录只能保存密文对象或密文分块，不得保存明文对象。
- manifest 可以保存 nonce、tag、plaintext_sha256、ciphertext_sha256、ciphertext_size_bytes，但不得保存明文数据加密密钥。
- manifest 内部同一 `data_key_id + nonce` 不得重复；中控端必须在解密前完成该校验，失败时拒绝整个 manifest。
- 单个对象大于单块运输盘容量时，manifest 必须按分块记录 `chunk_group_id`、`chunk_index`、`chunk_total`、`chunk_offset_bytes`、`chunk_size_bytes` 和 `chunk_sha256`。
- 跨盘分块默认大小固定为 `10 GiB`，即 `10 * 1024 * 1024 * 1024 = 10,737,418,240 bytes`。
- 除最后一个分块外，所有分块的 `chunk_size_bytes` 必须等于 `10 GiB`；最后一个分块可以小于或等于 `10 GiB`。
- `chunk_total` 最大值为 `1,000,000`，`chunk_index` 必须满足 `0 <= chunk_index < chunk_total`。
- 如果按 `10 GiB` 规划后 `chunk_total > 1,000,000`，边缘端必须拒绝导出该对象，错误码为 `CHUNK_INDEX_OVERFLOW`；不得写入 manifest。
- `chunked = false` 时，`chunk_group_id` 必须为空，`chunk_index = 0`，`chunk_total = 1`，`chunk_offset_bytes = 0`，`chunk_size_bytes = size_bytes`。
- `chunked = true` 时，`chunk_group_id`、`chunk_index`、`chunk_total`、`chunk_offset_bytes`、`chunk_size_bytes` 必须全部非空且合法。
- 中控端必须按 `edge_code + bucket + key + etag + size_bytes + last_modified + chunk_group_id` 聚合同一源对象的分块。
- 同一 `chunk_group_id` 下，`chunk_index` 必须从 0 到 `chunk_total - 1` 连续完整，且不得重复。
- 同一 `chunk_group_id` 下，按 `chunk_index` 排序后，第一个分块 `chunk_offset_bytes` 必须为 0，后一个分块的 `chunk_offset_bytes` 必须等于前一个分块的 `chunk_offset_bytes + chunk_size_bytes`。
- 同一 `chunk_group_id` 下，所有 `chunk_size_bytes` 之和必须等于源对象 `size_bytes`。
- 中控端必须把跨盘分块登记到 `chunk_import_group` 和 `chunk_import_part`；只有同一对象的全部分块到齐、偏移连续、总大小一致且全部校验通过后，才能合并导入中控 RustFS。
- manifest 缺失、JSON 解析失败、必填字段缺失、字段类型非法、顶层 `seal_id` 与 `disk_info.json.edge.seal_id` 不一致，或分块字段不连续时，必须拒绝导入并记录错误码 `MANIFEST_INVALID`。
- manifest SHA256、对象密文 SHA256、分块 SHA256 或解密后的明文 SHA256 与记录不一致时，必须拒绝当前 manifest 或对象并记录错误码 `CHECKSUM_MISMATCH`。
- 中控导入时必须使用 `bucket` 和 `key` 还原原始对象结构。

## 6. 中控归档规则

多个边缘端 RustFS 合并到一个中控 RustFS。

中控端根据 `disk_info.json` 中的 `edge.edge_code` 判断归档 bucket。

归档 bucket：

```text
archive-{edge_code}
```

导入 key：

```text
{source_bucket}/{source_object_key}
```

示例：

```text
边缘端：
edge_code = site001
bucket = photos
key = 2026/08/08/a.jpg

中控端：
bucket = archive-site001
key = photos/2026/08/08/a.jpg
```

规则：

- `edge_code` 在边缘注册阶段保证全局唯一。
- `edge_code` 在边缘注册阶段保证满足 S3 bucket 命名要求。
- 中控端发现 `archive-{edge_code}` 不存在时自动创建。
- 中控端发现 `archive-{edge_code}` 已存在时直接复用。
- 中控端不得把不同边缘端数据导入同一个归档 bucket。

## 7. 硬盘热插拔规则

两端都要实现硬盘实时监控。

程序启动：

```text
扫描当前已存在硬盘
-> 识别候选运输盘
-> 读取 SN、容量、文件系统、挂载点
-> 校验注册状态和协议文件
```

程序运行中：

```text
监听 Linux udev add/remove/change
-> 新盘插入后进入校验流程
-> 拔盘后更新任务状态和前端状态
```

如果导出、导入、清理或重新初始化过程中收到 remove 事件，必须立即停止当前盘后续 I/O，`disk_runtime.status = REMOVED`，`disk_runtime.last_error_code = DISK_REMOVED`；重新插入后必须按恢复规则处理，不得直接继续原操作。

进入任务池条件：

- SN 已注册。
- `disk_id` 匹配中控记录。
- 当前物理盘运行时检测到的文件系统必须为 `ext4`，该校验由当前端本地完成，不通过 HTTP API 上报；不满足时必须拒绝进入任务池，错误码 `FILESYSTEM_UNSUPPORTED`。
- 容量符合中控登记信息。
- `disk_info.json` 协议版本兼容；版本不兼容或缺少当前版本必需字段时必须拒绝进入任务池，错误码 `PROTOCOL_VERSION_UNSUPPORTED`。
- `status.code` 符合当前端可处理状态。

强行拔盘、断电或服务重启后的重插恢复规则：

运输盘在写入对象、写入 manifest、导入对象或更新 `disk_info.json` 时发生强行拔盘、断电或服务进程退出，盘内 `disk_info.json.status.code` 可能停留在旧状态。重新插入后，程序不得只看盘内状态就直接继续导出、导入、清理或重新初始化，必须先记录 `RECOVERY_REQUIRED`，再结合本地任务账本、盘内文件和中控导入账本做恢复判定。

| 重新插入时的盘内状态/文件情况 | 判定方 | 处理规则 | 禁止动作 |
|---|---|---|---|
| `status.code = EDGE_COPYING`，无有效 manifest，存在边缘端本地 `export_job` 且任务未完成 | 边缘端 | 进入导出恢复检查。删除或隔离 `.partial` 临时文件；已校验完成且已写入本地 `export_object.status = EXPORTED` 的最终密文文件可以保留；未完成对象回到 `PENDING` 或标记 `FAILED` 后重试。恢复检查完成前 `disk_runtime.status = CHECKING`。 | 中控端导入；边缘端清理；直接封盘。 |
| `status.code = EDGE_COPYING`，无有效 manifest，找不到匹配的边缘端本地 `export_job` | 边缘端 | 标记为不可自动恢复，`disk_runtime.status = ERROR`，错误码 `ORPHAN_EDGE_COPYING`。需要人工确认后才能重置为 `INITIALIZED`。 | 自动继续导出；自动清理；自动封盘。 |
| `status.code = EDGE_COPYING`，但 manifest、manifest SHA256、路径约束、nonce 唯一性和对象加密校验均有效 | 边缘端或中控端 | 按“封盘完成但状态未落盘”的情况处理。边缘端可将 `disk_info.json.status.code` 修复为 `SEALED`；中控端完成导入前校验后可按 `SEALED` 导入。 | 把有效封盘数据当作未导入数据清理。 |
| `status.code = SEALED`，manifest、manifest SHA256、路径约束、nonce 唯一性和对象加密校验均有效 | 中控端 | 可以幂等导入。导入前必须查询 `object_ledger` 跳过已导入对象；不得重复上传已入账对象。 | 边缘端写入；边缘端清理；重复封盘。 |
| `status.code = CENTER_IMPORTING`，存在匹配 `disk_id + seal_id` 的 `import_job` 且状态不是 `DONE` | 中控端 | 进入导入恢复。普通对象以 `object_ledger` 为准跳过已成功导入对象，跨盘分块以 `chunk_import_part` 为准跳过已登记且校验通过的分块；恢复后仍使用原 `import_job_id` 或在新任务中记录 `recovered_from_import_job_id`。 | 重新初始化；清理封存数据；把任务直接标记 `IMPORTED`。 |
| `status.code = CENTER_IMPORTING`，找不到匹配 `disk_id + seal_id` 的活动 `import_job` | 中控端 | 标记为不可自动恢复，`disk_runtime.status = ERROR`，错误码 `ORPHAN_CENTER_IMPORTING`。需要人工根据 manifest 和账本决定修复为 `SEALED` 继续导入，或修复为 `ERROR`。 | 自动清理；自动重新初始化；直接标记 `IMPORTED`。 |
| `status.code = IMPORTED`，`import_job.status = DONE` 且有效对象均已入账 | 中控端 | 允许进入清理和重新初始化流程；清理完成并写入新的 `disk_info.json` 后才变为 `INITIALIZED`。 | 再次按封盘数据导入；未重新初始化就交付边缘端写入。 |
| `status.code = IMPORTED`，`import_job.status = DONE`，且 `disk_runtime.status = ERROR` / `last_error_code = REINIT_FAILED` | 中控端 | 导入结果保持完成，不得回滚 `import_job.status`。盘内主状态保持 `IMPORTED`，只允许中控端继续清理封存数据或重新初始化；全部成功后最后一步才写入新的 `disk_info.json.status.code = INITIALIZED`。 | 再次按封盘数据导入；交付边缘端写入；把 `CLEANING` 或 `REINITIALIZING` 写入盘内 `status.code`。 |
| 任意状态下存在 `.partial` 文件 | 当前处理端 | `.partial` 只能作为未完成临时文件处理。恢复检查时必须优先删除；删除失败时移动到 `/rustfs-transfer/quarantine/partial/`；删除或隔离成功后记录 `PARTIAL_CLEANED`，重新计算 `free_bytes`，对应 `COPYING` 对象回到 `PENDING` 或标记 `FAILED`。删除和隔离均失败时，`disk_runtime.status = ERROR`，错误码 `PARTIAL_CLEAN_FAILED`。 | 导入 `.partial`；把 `.partial` 计入 `manifest.object_count` 或 `manifest.total_bytes`；清理失败仍继续封盘。 |

中文说明：

- `EDGE_COPYING` 残留通常表示边缘端还没完整封盘，可能只有一部分对象写完。此时不能让中控导入，也不能直接清理，必须先由边缘端确认哪些对象已经完整写好、哪些对象需要重试。
- `SEALED` 表示封盘资料完整，是中控端可以导入的唯一正常入口。只要 manifest、manifest SHA256、路径约束、nonce 唯一性和对象加密校验有效，即使之前发生过服务重启，也应按幂等导入处理。
- `CENTER_IMPORTING` 残留通常表示中控端导入中断。此时不能重新初始化，因为盘里可能还有尚未导入的数据；必须先用 `disk_id + seal_id` 找到对应导入任务，再查看 `object_ledger` 和 `chunk_import_part`，已入账对象或已校验分块跳过，未完成条目继续导入。
- 找不到匹配任务账本的 `EDGE_COPYING` 或 `CENTER_IMPORTING` 属于任务丢失，系统不能自动猜测数据是否完整，必须进入人工修复。
- `.partial` 残留只代表某个对象或分块未完成，不代表已校验对象损坏。已写入最终密文文件且本地 `export_object.status = EXPORTED` 的对象可以保留；未完成对象必须重试或失败，`.partial` 不得参与封盘和导入。
- `IMPORTED` 只表示导入已经完成，不表示运输盘已经可写。清理和重新初始化失败时，`import_job.status = DONE` 和盘内 `status.code = IMPORTED` 都不得回滚；系统只能继续复用流程，不能重复导入同一封盘批次。

## 8. 边缘端导出契约

边缘端只允许对 RustFS 执行：

```text
List
HEAD
GET
```

边缘端禁止：

```text
Delete 源对象
Put 源对象
修改源对象 metadata
```

导出流程：

```text
发现运输盘
-> 请求中控校验 SN/disk_id
-> 判断运输盘是否可写
-> 更新 disk_info 为 EDGE_COPYING
-> 扫描 RustFS 对象
-> 稳定性判断
-> 本地去重
-> 按 free_bytes 扣除预留空间计算对象可用容量
-> 多盘任务分配
-> 流式读取 RustFS 对象并使用 AES-256-GCM 加密写入 .partial
-> 内存 ProgressAggregator 实时累计对象、分盘和全局进度
-> WebSocket 直接推送内存进度快照
-> 计算密文 SHA256
-> 记录 nonce、tag、ciphertext_sha256 和 ciphertext_size_bytes
-> 写 meta sidecar
-> fsync .partial 文件和 meta sidecar
-> 原子重命名为最终密文文件
-> fsync /rustfs-transfer/data/ 与 /rustfs-transfer/meta/ 父目录
-> 生成本次 seal_id
-> 封盘前扫描确认不存在 .partial
-> 写 manifest
-> 写 manifest SHA256
-> fsync manifest、manifest SHA256 和父目录
-> 写入 disk_info.edge.seal_id
-> 更新 disk_info 为 SEALED
```

`.partial` 写盘规则：

- 边缘端写对象或分块时必须先写入 `.partial` 临时密文文件，路径必须记录到 `export_object.partial_path`。
- 对象进入 `COPYING` 后，当前对象 `done_bytes`、`remaining_bytes`、`speed_bytes_per_sec`、分盘进度和全局进度必须由流式写入引擎在内存中实时计算。
- WebSocket `COPY_PROGRESS` 直接读取内存 `ProgressAggregator`，不得每秒查询或聚合 `export_job`、`export_object`、`disk_runtime` 生成实时进度。
- 边缘端数据库只记录对象生命周期关键节点：`PENDING`、`ASSIGNED`、`COPYING`、`EXPORTED`、`FAILED`、`SOURCE_CHANGED`、`SKIPPED`；`export_job` 只保存任务阶段、低频 checkpoint 和最终结果。
- `export_object.status`、`export_job.status`、对象分配锁、nonce 唯一记录、错误码和封盘结果属于关键状态变更，必须立即事务写入，不得延迟到低频 checkpoint。
- 只有同时满足对象读取完成、AES-GCM tag 已生成、`ciphertext_sha256` 计算完成、metadata sidecar 写入成功、文件和父目录 `fsync` 成功后，才允许把 `.partial` 原子重命名为最终密文文件。
- `.partial` 永远不得写入 `export_manifest.json`，不得被中控端导入，也不得计入 `manifest.object_count`、`manifest.total_bytes` 或 `object_ledger`。
- `.partial` 在恢复扫描时一律视为未完成残留，不允许根据文件大小猜测为成功对象。

写盘过程中磁盘满处理：

- 如果写 `.partial`、metadata、manifest、日志或协议文件时发生 `ENOSPC` / no space left on device，必须记录错误码 `DISK_FULL`。
- 当前对象或分块必须停止写入并关闭文件句柄；对应 `export_object.status` 写为 `FAILED`，`export_object.error_code = DISK_FULL`。
- 当前对象或分块的 `.partial` 必须删除；删除失败时移动到 `/rustfs-transfer/quarantine/partial/`。删除或隔离均失败时，`disk_runtime.status = ERROR`，错误码 `PARTIAL_CLEAN_FAILED`。
- 清理完成后必须重新读取 `free_bytes` 并更新 `disk_runtime.free_bytes`、`reserve_bytes`、`object_budget_bytes`。
- 当前运输盘停止接收新对象；已完成且校验通过的 `EXPORTED` 对象保持有效。
- 如果至少存在一个 `EXPORTED` 对象，允许进入封盘前校验并封盘；如果没有任何 `EXPORTED` 对象，当前盘不得生成空 manifest，应保持可重新分配状态或按任务策略标记失败。

封盘前校验：

- 封盘前必须扫描 `/rustfs-transfer/data/`、`/rustfs-transfer/meta/` 和 `/rustfs-transfer/logs/`，确认不存在任何 `.partial`。
- manifest 只能包含 `export_object.status = EXPORTED` 且最终密文文件、metadata sidecar、SHA256 和 AES-GCM tag 均完整的对象或分块。
- 如果封盘前发现 `.partial`，必须执行恢复清理流程；清理成功后记录 `PARTIAL_CLEANED` 并重新计算空间，清理失败则记录 `PARTIAL_CLEAN_FAILED`，不得封盘。
- manifest、manifest SHA256、`disk_info.json` 和父目录必须写入并 `fsync` 成功；如果这些协议文件因空间不足无法写入，必须记录 `DISK_FULL`，不得把状态更新为 `SEALED`。

对象稳定性规则：

```text
last_modified 早于当前时间 N 分钟
-> 第一次 HEAD
-> 等待 30-60 秒
-> 第二次 HEAD
-> size、etag、last_modified 一致
-> 下载对象
-> 下载后再次 HEAD
-> 源对象仍未变化
```

## 9. 中控端导入契约

中控端导入流程：

```text
发现运输盘
-> 校验 SN/disk_id
-> 读取 disk_info.json
-> 校验 center_signature 覆盖的中控初始化字段
-> 确认 status.code 必须为 SEALED
-> 读取 seal_id、export_job_id 和 manifest_sha256
-> 在数据库事务中获取 disk_id + seal_id 的导入锁
-> 更新 disk_info 为 CENTER_IMPORTING
-> 校验 manifest 格式、seal_id/export_job_id 和 manifest_sha256
-> 校验 manifest 内部和历史账本中 data_key_id + nonce 未重复
-> 普通对象：校验密文 ciphertext_sha256
-> 普通对象：解密并校验 plaintext_sha256
-> 跨盘分块：登记 chunk_import_group 和 chunk_import_part
-> 跨盘分块：校验当前分块 ciphertext_sha256、tag、AAD 和分块字段合法性
-> 跨盘分块：复制当前分块密文到中控端本地 staging 并 fsync
-> 跨盘分块：等待同一 chunk_group_id 的全部分块到齐
-> 跨盘分块：全部分块到齐后按 chunk_index 顺序合并并校验整体 plaintext_sha256
-> 根据 edge_code 创建或复用 archive-{edge_code}
-> 查询 object_ledger 去重
-> 上传对象到中控 RustFS
-> 上传成功后写 object_ledger
-> 本盘全部普通对象导入完成且全部跨盘分块登记校验完成后更新 disk_info 为 IMPORTED
-> import_job.status = DONE
-> disk_runtime.status = CLEANING
-> 清理运输盘封存数据
-> disk_runtime.status = REINITIALIZING
-> 重新初始化并写入新的 disk_info.json
-> 更新 disk_info 为 INITIALIZED
-> disk_runtime.status = DONE
```

导入幂等规则：

- `seal_id` 是封盘批次 ID，不是运输盘 ID。`disk_id` 可以在重新初始化后重复使用，但每次封盘必须生成新的 `seal_id`。
- 中控端开始导入前，必须以 `disk_id + seal_id` 判断是否已有活动导入任务；同一 `disk_id + seal_id` 只能存在一个 `PENDING` 或 `IMPORTING` 任务。
- 如果同一 `disk_id + seal_id` 已有 `DONE` 任务，且 `manifest_sha256` 一致，中控端必须视为该封盘批次已导入，跳过重复导入。
- 如果同一 `disk_id + seal_id` 已有任务但 `manifest_sha256` 不一致，必须拒绝导入并标记协议异常，错误码 `SEAL_ID_MANIFEST_MISMATCH`。
- `object_ledger` 必须有唯一约束。
- 唯一键为 `edge_code + source_bucket + source_key + source_etag + source_size_bytes + source_last_modified`。
- `object_ledger` 不增加对象导入中间状态字段，只记录已上传成功的对象。
- 普通对象上传成功后才能写入 `object_ledger`。
- 普通对象写入 `object_ledger` 时必须记录该对象的 `data_key_id + nonce`。
- 跨盘对象合并上传成功后才能写入 `object_ledger`，并且必须记录 `chunk_group_id`；不得把任一分块的 `data_key_id + nonce` 当作整体对象账本的 nonce。
- 导入前查询 `object_ledger` 已存在同一唯一键时，必须跳过该对象，不得重复上传。
- 并发场景下，如果上传成功后写入 `object_ledger` 命中唯一键冲突，必须视为其他 Worker 已完成同一来源对象版本入账，当前 Worker 不得再写重复账本。
- 普通对象以 `object_ledger` 写入成功作为对象导入完成；跨盘对象以 `chunk_import_group.status = DONE` 且 `object_ledger` 写入成功作为对象导入完成。
- 导入失败不得写 `IMPORTED`。
- manifest 格式、必填字段、顶层 `seal_id` / `export_job_id` 或分块连续性校验失败时，错误码必须为 `MANIFEST_INVALID`。
- manifest SHA256、对象密文 SHA256、分块 SHA256 或解密后明文 SHA256 校验失败时，错误码必须为 `CHECKSUM_MISMATCH`。
- 按 `data_key_id` 找不到可用于历史导入的密钥，或 AES-GCM tag 验证失败、解密失败时，错误码必须为 `DECRYPT_FAILED`。

跨盘分块导入规则：

- 中控端处理 `chunked = false` 的 manifest 对象时，按普通对象导入；成功上传中控 RustFS 后直接写入 `object_ledger`。
- 中控端处理 `chunked = true` 的 manifest 对象时，不得直接写入 `object_ledger`，必须先登记 `chunk_import_group` 和 `chunk_import_part`。
- 首个分块到达时创建 `chunk_import_group`，状态为 `WAITING_PARTS`；后续分块到达时必须校验源对象身份字段与分组表完全一致。
- 同一 `chunk_group_id + chunk_index` 已存在且字段完全一致时，按重复插盘或重复任务幂等处理；字段不一致时拒绝当前 manifest，错误码为 `MANIFEST_INVALID`。
- 同一 `data_key_id + nonce` 已存在于 `chunk_import_part` 或 `object_ledger` 且不是同一分块的幂等重放时，必须拒绝当前 manifest，错误码为 `NONCE_REUSED`。
- 当前分块完成路径校验、密文 SHA256 校验、AES-GCM tag 验证、AAD 校验、本地 staging 密文写入和暂存目录 `fsync` 后，`chunk_import_part.status = VERIFIED`。
- 中控端本地 staging 目录固定为 `/var/lib/rustfs-transfer/chunks/`；`chunk_import_part.staged_ciphertext_path` 必须是相对于该目录的相对路径，不得以 `/` 开头，不得包含 `..`。
- `chunk_import_part.staged_ciphertext_sha256` 必须与 manifest 中该分块的 `ciphertext_sha256` 一致；合并前必须再次校验 staging 文件 SHA256。
- 当同一 `chunk_group_id` 下 `VERIFIED` 分块数量等于 `chunk_total`，且 `chunk_index` 从 `0` 到 `chunk_total - 1` 连续、偏移连续、分块大小之和等于源对象 `size_bytes` 时，`chunk_import_group.status = READY_TO_MERGE`。
- 进入 `READY_TO_MERGE` 后，中控端必须获取 `chunk_group_id` 合并锁，把 `chunk_import_group.status` 更新为 `MERGING`，再按 `chunk_index` 顺序读取 staging 密文、流式解密合并并上传中控 RustFS。
- 合并上传完成后，必须校验整体 `plaintext_sha256`，然后写入一条带 `chunk_group_id` 的 `object_ledger` 记录表达该源对象已导入；所有 `chunk_import_part.status` 更新为 `MERGED`，`chunk_import_group.status` 更新为 `DONE`。
- 合并、上传、整体校验或写账本任一步失败时，`chunk_import_group.status = FAILED`，写入标准错误码和错误信息；已登记且校验通过的分块保留，用于人工排查或重新触发合并。
- 单个运输盘导入任务只负责登记和校验本盘包含的分块；该盘可以在分块登记和校验成功后完成本盘 `import_job`，但跨盘对象只有在 `chunk_import_group.status = DONE` 且 `object_ledger` 已写入后，才表示对象已完整导入。
- 清理运输盘封存数据前，本盘所有跨盘分块必须已经持久化到中控端 staging 并进入 `VERIFIED`；否则不得清理该盘上的分块密文文件。
- 前端导入进度必须区分“本盘导入完成”和“跨盘分块等待中”；存在 `WAITING_PARTS` 的跨盘对象时，不得向用户展示该对象已完成归档。

清理和重新初始化运行态规则：

- `CLEANING` 和 `REINITIALIZING` 是 `disk_runtime.status` 运行态，只用于中控端当前操作和前端展示，不属于盘内主生命周期。
- 中控端写入 `disk_info.json.status.code = IMPORTED` 且 `import_job.status = DONE` 后，导入结果即视为完成；后续清理或重新初始化失败不得回滚 `import_job.status`，也不得把该封盘批次重新导入。
- 进入清理旧数据前，必须写入 `disk_runtime.status = CLEANING`。
- 清理封存数据全部成功后，才能写入 `disk_runtime.status = REINITIALIZING` 并开始创建新的目录结构、生成新的 `data_key_id + disk_data_key`、写入新的 `disk_info.json`。
- 只有新目录结构、新 `disk_info.json`、签名、新密钥绑定和父目录 `fsync` 全部成功后，最后一步才允许把盘内 `disk_info.json.status.code` 写为 `INITIALIZED`，并把 `disk_runtime.status` 写为 `DONE`。
- 如果清理或重新初始化任一步失败，盘内 `disk_info.json.status.code` 必须保持 `IMPORTED`，`disk_runtime.status = ERROR`，`disk_runtime.last_error_code = REINIT_FAILED`。
- 重新初始化失败时，新生成但尚未完整写入盘内并完成签名/`fsync` 的 `data_key_id + disk_data_key` 不得置为可发放状态，不得通过 `/api/disk/export-key` 返回给边缘端；下一次重试必须重新生成新的 `data_key_id + disk_data_key`。
- 旧 `data_key.status` 只有在重新初始化全部成功后才从 `SEALED_READONLY` 更新为 `RETIRED`；如果清理或重新初始化失败，旧密钥状态不得提前退役，以便中控端保留必要的历史校验和人工恢复能力。
- `REINIT_FAILED` 后续只允许中控端继续清理或重新初始化；不得再次按 `SEALED` 封盘数据导入，不得交付边缘端写入。

避免状态混淆：

- `disk_info.json.status.code` 表示运输盘主生命周期，只能使用 `UNREGISTERED`、`REGISTERED`、`INITIALIZED`、`EDGE_COPYING`、`SEALED`、`CENTER_IMPORTING`、`IMPORTED`、`ERROR`。
- `disk_runtime.status` 表示当前机器对运输盘执行的运行/操作状态，可以出现 `CLEANING`、`REINITIALIZING`。
- 禁止把 `CLEANING`、`REINITIALIZING` 写入 `disk_info.json.status.code`、manifest 或 `import_job.status`。
- 边缘端是否可写仍只看盘内 `status.code = INITIALIZED`；`disk_runtime.status = DONE` 不能单独作为可写依据。
- 中控端是否可重复导入仍以 `disk_id + seal_id + import_job.status` 和 `object_ledger` 为准；`REINIT_FAILED` 不能触发重复导入。

导入并发锁规则：

```text
开始导入 SEALED 运输盘
-> 读取 disk_id、seal_id、export_job_id、manifest_sha256
-> 生成 import_job_id
-> BEGIN
-> INSERT import_job(import_job_id, disk_id, seal_id, export_job_id, manifest_sha256, status = IMPORTING)
   ON CONFLICT(disk_id, seal_id) WHERE status IN (PENDING, IMPORTING, DONE)
   DO NOTHING
-> 如果插入成功：当前 Worker 获得该封盘批次导入权
-> 如果插入失败：查询同一 disk_id + seal_id 的已有任务
   -> 已有任务为 PENDING 或 IMPORTING：说明已有 Worker 正在导入同一封盘批次，当前 Worker 必须退出或只订阅进度
   -> 已有任务为 DONE 且 manifest_sha256 一致：说明该封盘批次已导入完成，当前 Worker 必须跳过
   -> 已有任务的 manifest_sha256 不一致：拒绝导入并记录 SEAL_ID_MANIFEST_MISMATCH
-> COMMIT
```

中文说明：

- `disk_id` 表示这块运输盘本身，会随着硬盘复用一直保持稳定。
- `seal_id` 表示这一次封盘产生的数据批次，每次边缘端封盘都必须重新生成。
- 多 Worker 防重不能只看 `disk_id`，否则同一块盘历史批次和当前批次会混在一起；也不能完全不加锁，否则两个 Worker 可能同时导入同一个封盘。
- 正确判断单位是 `disk_id + seal_id`：同一块盘、同一次封盘，只能有一个 Worker 导入。

导入进度与落库规则：

- `import_job` 在导入任务开始时创建，初始状态为 `IMPORTING`。
- 导入过程中，前端实时进度以 WebSocket 推送为准。
- `import_job` 只保存低频汇总进度，不按每个字节或每个小块更新数据库。
- 导入过程中在内存累计 `imported_count` 和 `imported_bytes`。
- 满足以下任一条件时，更新一次 `import_job` 汇总字段：
  - 距离上次更新 >= 1 秒。
  - 距离上次更新已完成 >= 100 个对象。
  - 当前导入任务完成、失败或取消。
- 导入完成时，`import_job.status = DONE`，并写入 `finish_time`。
- 导入失败时，`import_job.status = FAILED`，写入 `error_message` 和 `finish_time`。
- `object_ledger` 采用对象成功后立即写入，不做批量写入。

WebSocket 与数据库边界：

- WebSocket 负责高频推送当前进度、速度、当前对象和剩余字节数；运行中进度来源必须是内存 `ProgressAggregator` 快照。
- 边缘端导出时，`ProgressAggregator` 由流式写 `.partial` 的 DiskWorker 更新；中控端导入时，`ProgressAggregator` 由 ImportWorker 在对象校验、解密和上传过程中更新。
- `export_job` 和 `import_job` 只保存任务级低频 checkpoint、阶段状态和最终结果，用于任务恢复、审计和页面首次加载后的状态恢复。
- `object_ledger` 只保存对象导入成功记录，用于去重、幂等和来源追踪；不得为了 1 秒 WebSocket 推送扫描 `object_ledger` 统计实时导入进度。
- 运行中的 WebSocket tick 不得每秒扫描或聚合 `export_job`、`export_object`、`disk_runtime`、`import_job`、`object_ledger`。
- 对象完成、失败、源对象变化、跳过、盘级异常、导入账本、导入完成等关键状态变更仍必须立即写库，不属于低频 checkpoint。

## 10. 多盘并行契约

边缘端：

```text
待导出对象队列
-> 数据库事务分配对象
-> 每块运输盘一个 DiskWorker
-> 每个 DiskWorker 控制本盘对象并发
-> 普通对象只能分配给一块运输盘
-> 跨盘大对象按分块分配，每个分块只能分配给一块运输盘
```

对象分配锁规则：

- 多个 DiskWorker 并发分配对象时，必须以 PostgreSQL 作为最终锁来源，不得只依赖进程内互斥锁。
- 抢占待分配对象必须在同一个数据库事务中完成，使用 `SELECT ... FOR UPDATE SKIP LOCKED` 锁定 `export_object` 行，再把锁定行更新为 `ASSIGNED` 并写入目标 `disk_id`。
- 已进入 `ASSIGNED`、`COPYING` 或 `EXPORTED` 的对象或分块不得再次被其他运输盘抢占。
- 普通对象的分配唯一性以 `export_job_id + bucket + object_key + etag + size_bytes + last_modified` 为准。
- 分块对象的分配唯一性以 `chunk_group_id + chunk_index` 为准；同一分块不得被分配到多个运输盘。
- 如果唯一约束冲突或 `UPDATE ... RETURNING` 返回空结果，Worker 必须视为未抢到该对象，重新拉取下一批，不得继续写盘。

事务写法：

```sql
BEGIN;

WITH candidate AS (
  SELECT id
       , chunk_size_bytes
  FROM export_object
  WHERE export_job_id = :export_job_id
    AND status = 'PENDING'
    AND disk_id IS NULL
    AND chunk_size_bytes <= :object_budget_bytes
  ORDER BY id ASC
  FOR UPDATE SKIP LOCKED
  LIMIT :candidate_limit
),
picked AS (
  SELECT id
  FROM (
    SELECT id,
           SUM(chunk_size_bytes) OVER (ORDER BY id ASC) AS running_bytes
    FROM candidate
  ) AS ranked
  WHERE running_bytes <= :object_budget_bytes
  LIMIT :batch_size
)
UPDATE export_object AS eo
SET status = 'ASSIGNED',
    disk_id = :disk_id
FROM picked
WHERE eo.id = picked.id
RETURNING eo.id, eo.bucket, eo.object_key, eo.chunked, eo.chunk_group_id, eo.chunk_index, eo.chunk_size_bytes;

COMMIT;
```

实现要求：

- `SELECT ... FOR UPDATE SKIP LOCKED` 和 `UPDATE ... RETURNING` 必须在同一个事务中执行。
- Worker 只能拷贝 `RETURNING` 返回的对象或分块。
- 单个事务内分配的 `chunk_size_bytes` 总和不得超过当前运输盘重新计算后的 `object_budget_bytes`；批量装箱必须在事务中按累计容量筛选，不能在事务外先读后写。
- 事务失败、连接断开或提交失败时，Worker 不得假定分配成功；必须重新查询数据库确认对象状态。

分块分配规则：

- 跨盘分块默认大小固定为 `10 GiB`，即 `10,737,418,240 bytes`。
- 除最后一个分块外，所有分块大小必须等于 `10 GiB`；最后一个分块可以小于或等于 `10 GiB`。
- `chunk_total` 最大值为 `1,000,000`，超过该限制时对象必须标记为 `FAILED` 或 `SKIPPED`，错误码 `CHUNK_INDEX_OVERFLOW`。
- `chunked = false` 时，同一对象只能有一条 `export_object` 记录进入 `ASSIGNED` 或 `COPYING`。
- `chunked = true` 时，同一对象可以有多条 `export_object` 分块记录，但必须共用同一个 `chunk_group_id`。
- 同一个 `chunk_group_id` 下，`chunk_index` 必须从 0 到 `chunk_total - 1` 连续完整。
- 同一个 `chunk_group_id` 下，`chunk_offset_bytes` 必须从 0 开始按 `chunk_index` 连续递增，后一分块偏移必须等于前一分块偏移加前一分块大小。
- 同一个 `chunk_group_id` 下，所有 `chunk_size_bytes` 之和必须等于源对象 `size_bytes`。
- 同一个 `chunk_group_id + chunk_index` 不得被分配到多个运输盘。
- 任一分块失败时，该源对象整体不得标记为完整导出；已成功分块可以保留用于任务恢复。

对象任务状态：

| 状态码 | 中文名称 | 状态含义 | 主要写入方 | 允许动作 | 下一步状态 |
|---|---|---|---|---|---|
| `PENDING` | 待分配 | 对象已通过扫描和稳定性初筛，等待调度到某块运输盘。 | 边缘端 | 分配到具体运输盘。 | `ASSIGNED` 或 `SKIPPED` |
| `ASSIGNED` | 已分配 | 对象已被分配给某块运输盘，但尚未开始下载。用于防止多盘并行时重复分配。 | 边缘端 | 开始下载。 | `COPYING` |
| `COPYING` | 拷贝中 | 对象或分块正在从边缘 RustFS 流式读取，并加密写入运输盘 `.partial` 临时密文文件。 | 边缘端 | 继续下载、加密、计算进度。 | `EXPORTED`、`SOURCE_CHANGED` 或 `FAILED` |
| `EXPORTED` | 已导出 | 对象或分块已完整加密写入运输盘，密文 SHA256 校验通过，最终密文文件和 metadata 已落盘。边缘端本地对象生命周期到此结束，不表达中控是否已导入。 | 边缘端 | 写入 manifest；等待运输盘封盘和中控导入。 | 保持 `EXPORTED` |
| `FAILED` | 失败 | 对象导出失败，失败原因应写入错误信息。 | 边缘端 | 按对象级重试；前端展示。 | `PENDING`、`COPYING` 或保持 `FAILED` |
| `SOURCE_CHANGED` | 源对象变化 | 对象下载前后 HEAD 结果不一致，说明源对象可能正在上传、覆盖或变更。 | 边缘端 | 跳过本轮导出；下轮重新扫描。 | `PENDING` 或 `SKIPPED` |
| `SKIPPED` | 已跳过 | 对象因本轮已导出、按需查询中控账本确认已导入、容量不足、规则排除等原因被跳过。 | 边缘端 | 记录原因；不进入有效 manifest。 | 保持 `SKIPPED` |

中控端：

```text
多个 SEALED 运输盘
-> 每块运输盘一个 ImportWorker
-> 导入前查询 object_ledger
-> 已导入跳过
-> 未导入上传
-> 上传成功后写账本
```

## 11. 数据库边界

详细数据库表、字段备注和关键约束见：[数据库设计.md](数据库设计.md)。

中控端数据库是权威库，负责：

- 运输盘注册。
- 边缘端注册。
- 运输盘注册和启用状态。
- 运输盘数据加密密钥。
- 中控归档 bucket。
- 导入任务。
- 全局对象去重账本。

边缘端数据库是本地运行账本，负责：

- RustFS 对象扫描快照。
- 导出任务。
- 导出对象状态。
- 本地运输盘运行状态。
- 程序重启后的恢复。
- 边缘前端实时展示数据来源。

关键原则：

- 中控端最终导入判断只认中控数据库和运输盘协议。
- 边缘端不可直接修改中控导入账本。
- 边缘端查询中控已导入对象只是优化，不是强依赖。
- 边缘端本地 `export_object.status` 不包含 `IMPORTED`；封盘寄出后对象保持 `EXPORTED`，中控是否已入库只由中控端 `object_ledger` / `import_job` 或只读按需查询接口表达。
- 中控端不可达但边缘端已完成硬盘校验并已领取本次 `disk_data_key` 时，边缘端可继续导出；该密钥不按时间过期。如果尚未领取数据加密密钥，则不得开始新的加密导出；运输盘进入 `SEALED` 后不得再领取同一 `data_key_id` 用于继续写入。

## 13. 已确认决策

### 13.1 已确认决策

- 运输硬盘不允许边缘端自动清盘。
- 运输盘落盘数据必须使用 AES-256 加密。
- 单个对象大于单块运输盘容量时，需要分块到多个运输硬盘处理。
- RustFS 导出范围为全部 bucket。
- 只做对象级重试，不做单对象断点续传。
- 中控端前端和边缘端前端独立部署。

### 13.2 密钥字段职责

- 授权码只用于边缘端调用中控 HTTP API 的鉴权，不直接用于文件加密。
- `edge_auth_secret` 用于 API 鉴权。
- `center_key_id` 用于中控签名密钥编号。
- `data_key_id` 用于 AES-256 数据加密密钥编号。
- 运输硬盘 SN 不作为业务主身份；业务主身份以中控初始化写入的 `disk_id` 为准，SN 只作为辅助校验。
- 如果边缘 RustFS 存在同名对象覆盖，中控端去重必须使用 `edge_code + source_bucket + source_key + source_etag + source_size_bytes + source_last_modified`，不能只用 bucket 和 key。
