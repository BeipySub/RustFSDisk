# 运输盘流式存储整改方案

## 1. 方案目标

当前系统仍处于开发模式，没有现场存量盘、没有上线历史包，因此本次整改按破坏性升级处理。

本方案不更换加密算法。继续使用 AES-256-GCM，删除旧的整对象落盘模式和旧 manifest 字段模型，通过调整运输盘存储结构、写入方式、导入方式和恢复索引解决传输慢、内存占用高、小文件 IO 过多、元数据破坏后恢复能力弱的问题。

本方案不修改 `docs/v1.0冻结/` 下的冻结文档。冻结文档仍作为 v1.0 基线；本文件作为开发阶段的 v2 整改补充方案。

## 2. 升级性质

本次升级定义为运输盘协议 v2。

- `disk_info.json.protocol.version` 调整为 `2.0.0`。
- `export_manifest.json.manifest_version` 调整为 `2.0.0`。
- Common 协议常量 `MANIFEST_VERSION` 必须同步调整为 `2.0.0`。
- `TransferDisk` 读写、校验和路径常量必须新增 `disk_info.bak.json`、`export_manifest.bak.json`、`export_manifest.bak.sha256`、`recovery_index.json`、`packs/`。
- Edge 端只生成 v2 盘面结构和 v2 manifest。
- Center 端只导入 v2 盘面结构和 v2 manifest。
- 主流程删除 v1 manifest 导出、导入和兼容解析。
- 主流程删除旧的单对象 `.bin` 文件存储模式。
- 主流程删除旧的对象级 `relative_data_path`、`nonce`、`tag`、`aad` 作为统一存储模型的设计。
- 旧测试数据、旧 fixture、旧 golden manifest 按 v2 重新生成。

本仓库 Edge/Center 主业务代码不提供旧盘读取能力，不提供旧盘迁移入口，不保留旧版本程序调用入口。

## 3. 旧逻辑删除范围

### 3.1 Edge 端删除

删除以下旧逻辑：

- `data/{export_job_id}/{object_id}.bin` 整对象文件写入。
- 以 `relative_data_path` 作为对象唯一数据位置的 manifest 模型。
- 对象级单一 `nonce/tag/aad` 作为所有对象存储模式的通用模型。
- `DiskWorker::export_one_object` 中整对象读入 `Vec<u8>`、整对象加密、整对象写盘的流程。
- v1 `export_manifest.json` 生成逻辑。
- 依赖旧 manifest 字段的导出测试。

### 3.2 Center 端删除

删除以下旧逻辑：

- v1 manifest 导入入口。
- 仅通过 `relative_data_path` 读取单对象密文文件的流程。
- `ManifestObject` 强制要求旧字段 `relative_data_path/nonce/tag/aad/encrypted/encryption_alg/ciphertext_sha256` 的模型。
- 依赖旧 manifest 字段的导入测试。

### 3.3 Common 删除与保留

保留：

- AES-256-GCM 加密/解密能力。
- HMAC 派生能力。
- SHA256 校验能力。
- 密钥不落明文盘的安全约束。

删除并替换：

- 旧 `object_aad(ObjectAad)` 作为唯一对象 AAD 的协议权威。
- 旧 manifest golden 中对 `relative_data_path` 单路径对象文件的依赖。
- `validate_manifest` 中只检查 `object.relative_data_path` 位于 `data/` 的逻辑。
- `TransferDisk::write_object_atomic(relative_data_path, bytes)` 作为主对象写入入口的逻辑。

新增并调整：

- `DiskStatusCode` 不增加 `RECOVERY_REQUIRED`。恢复检查开始时写入本地数据库 `disk_runtime.status = CHECKING`、`disk_runtime.last_error_code = RECOVERY_REQUIRED`。恢复失败时写入 `disk_runtime.status = ERROR` 并保留具体错误码。`RECOVERY_REQUIRED` 不写入盘内生命周期状态，也不作为 `runtime_status` 枚举值。
- `derive_disk_data_key_from_edge_key` 的域分离字符串升级为 `rustfs-transfer:offline-disk-data-key:v2`，该字符串必须定义为 Common 常量。Edge 和 Center 只调用 Common 函数计算派生密钥，并增加 golden vector 测试。禁止两端各自拼 KDF 字符串。
- Center 导入阶段不从 `data_key` 表读取明文 `disk_data_key`。Center 根据 `edge_code + disk_id + data_key_id + export_job_id + seal_id + edge_auth_secret` 调用 Common KDF 派生本次封盘 `disk_data_key`。Edge 导出阶段使用同一组输入调用 Common KDF 派生同一密钥。
- `disk_id` 和 `data_key_id` 的身份权威来自已通过 `center_signature` 校验的 `disk_info` 主文件、备份文件。`edge_code`、`export_job_id`、`seal_id` 必须在 `disk_info.edge`、`export_manifest.json` 和 `recovery_index.json` 三处完全一致；不一致时拒绝导入，错误码固定为 `MANIFEST_INVALID`。

## 4. v2 存储模型

v2 只保留两种存储模式：

- `PACK`：小对象合并写入 pack 文件。
- `FRAMES`：较大对象按固定 frame 分片写入。

不再保留 `FILE` 模式。

默认阈值：

| 参数 | 默认值 | 说明 |
|---|---:|---|
| `pack_object_threshold` | 64 MiB | 小于等于该值的对象进入 `PACK` |
| `pack_size_limit` | 1 GiB | 单个 pack 文件达到该值后滚动到下一个 pack |
| `frame_size` | 64 MiB | `FRAMES` 模式下单个 frame 的明文目标大小 |

对象分流规则：

- `size_bytes <= 64 MiB`：使用 `PACK`。
- `size_bytes > 64 MiB`：使用 `FRAMES`。

这里的“大文件”只作为是否进入分片模式的技术阈值，不代表业务上的超大文件。即使单个文件通常不超过 10 GiB，也必须避免整对象进入内存。

### 4.1 容量预算与多盘分配

v2 存储整改必须同步改造容量预算和多盘分配。分配任务时禁止只使用源对象 `size_bytes`，必须使用预计落盘大小 `estimated_landing_bytes`。

每块运输盘分配前必须重新读取文件系统剩余空间并计算：

```text
reserve_bytes = max(1 GiB, min(8 GiB, floor(free_bytes * 2 / 100)))
object_budget_bytes = free_bytes
  - reserve_bytes
  - estimated_manifest_bytes
  - estimated_metadata_bytes
  - estimated_log_bytes
  - encryption_overhead_bytes
```

`object_budget_bytes <= 0` 时，当前运输盘停止分配新对象，写入 `disk_runtime.last_error_code = INSUFFICIENT_SPACE`，不影响其他运输盘继续分配。

v2 固定估算参数：

| 参数 | 固定值 | 用途 |
|---|---:|---|
| `aes_gcm_tag_bytes` | 16 bytes | 每个 PACK 对象、每个 frame 的 GCM tag 元数据 |
| `aes_gcm_nonce_bytes` | 12 bytes | 每个 PACK 对象、每个 frame 的 nonce 元数据 |
| `aad_budget_bytes` | 512 bytes | 每个 PACK 对象、每个 frame 的 AAD base64 预算 |
| `manifest_object_base_bytes` | 4096 bytes | 每个 manifest object 公共字段预算 |
| `manifest_frame_bytes` | 1024 bytes | 每个 frame manifest 条目预算 |
| `object_meta_base_bytes` | 4096 bytes | 每个对象 meta sidecar 基础预算 |
| `pack_index_entry_bytes` | 512 bytes | 每个 PACK 对象 pack index 预算 |
| `recovery_file_entry_bytes` | 512 bytes | 每个 recovery index 文件条目预算 |
| `log_per_object_bytes` | 1024 bytes | 每个对象日志预算 |
| `filesystem_slack_per_file_bytes` | 4096 bytes | 每个新文件的文件系统块对齐预算 |

PACK 对象预计落盘大小：

```text
pack_estimated_landing_bytes =
  size_bytes
  + pack_index_entry_bytes
  + manifest_object_base_bytes
  + object_meta_base_bytes
  + aes_gcm_tag_bytes
  + aes_gcm_nonce_bytes
  + aad_budget_bytes
  + recovery_file_entry_bytes
  + log_per_object_bytes
  + filesystem_slack_per_file_bytes
```

FRAMES 对象预计落盘大小：

```text
frame_count = ceil(size_bytes / frame_size)

frames_estimated_landing_bytes =
  size_bytes
  + manifest_object_base_bytes
  + object_meta_base_bytes
  + frame_count * (
      manifest_frame_bytes
      + aes_gcm_tag_bytes
      + aes_gcm_nonce_bytes
      + aad_budget_bytes
      + recovery_file_entry_bytes
      + filesystem_slack_per_file_bytes
    )
  + log_per_object_bytes
```

容量分配规则：

- Edge Planner 必须在数据库事务内使用 `SELECT ... FOR UPDATE SKIP LOCKED` 锁定待分配对象。
- Edge Planner 必须按 `estimated_landing_bytes` 累加，不得按 `size_bytes` 累加。
- 同一事务返回的对象预计落盘总量不得超过当前运输盘重新计算后的 `object_budget_bytes`。
- 当前盘空间不足时，只停止当前盘继续分配，其他 `READY` 盘继续分配。
- 当前盘已存在 `EXPORTED` 对象且无法继续分配新对象时，进入封盘前校验。
- 当前盘没有任何 `EXPORTED` 对象且无法容纳下一个对象或 frame 时，该盘保持 `disk_info.status.code = INITIALIZED`，写入 `disk_runtime.last_error_code = INSUFFICIENT_SPACE`，不生成空 manifest。
- 写盘过程中发生 `ENOSPC` 时，当前对象或 frame 写入失败，错误码固定为 `DISK_FULL`；已经完整写入并校验通过的对象保留。
- 写 manifest、metadata、recovery index、hash 文件、日志时发生 `ENOSPC`，当前盘不得封盘，写入 `disk_runtime.status = ERROR`、`disk_runtime.last_error_code = DISK_FULL`。

跨盘分配规则：

- `PACK` 对象必须整体分配到一块运输盘，不跨盘拆分。
- `FRAMES` 对象以 frame 为容量分配单元。
- 单个 FRAMES 对象的 frame 允许分配到多块运输盘。
- 每块运输盘的 v2 manifest 只记录分配到本盘的 frame。
- 同一源对象的所有 frame 必须使用同一个 `object_id`、`frame_total`、`plaintext_sha256`。
- Center 以 `object_id + frame_index` 汇总跨盘 frame，所有 frame 到齐且对象级 `plaintext_sha256` 校验通过后，才能写入 `object_ledger`。
- 单个 frame 的 `estimated_landing_bytes` 大于所有 `READY` 运输盘的 `object_budget_bytes` 时，该源对象标记为 `SKIPPED`，错误码固定为 `INSUFFICIENT_SPACE`。

## 5. v2 运输盘目录结构

```text
/rustfs-transfer/
  disk_info.json
  disk_info.bak.json

  manifests/
    export_manifest.json
    export_manifest.bak.json
    export_manifest.sha256
    export_manifest.bak.sha256
    recovery_index.json

  packs/
    pack-000001.dat
    pack-000001.idx
    pack-000002.dat
    pack-000002.idx

  data/
    {export_job_id}/
      {object_id}/
        000000.frame
        000001.frame

  meta/
    meta-pack-000001.jsonl
    {export_job_id}/
      {object_id}.json

  logs/
  quarantine/
    partial/
```

约束：

- 不再生成 `data/{export_job_id}/{object_id}.bin`。
- `packs/*.dat` 存放多个小对象密文片段。
- `packs/*.idx` 存放 pack 内对象索引，便于快速恢复和局部定位。
- `data/{export_job_id}/{object_id}/*.frame` 存放较大对象的加密分片。
- `meta/` 存放对象级冗余元数据。
- `manifests/` 存放主 manifest、备份 manifest、哈希文件和恢复索引。
- 封盘前必须扫描并处理 `.partial` 文件。存在 `.partial` 文件时封盘失败，Edge 写入本地数据库 `disk_runtime.status = CHECKING`、`disk_runtime.last_error_code = RECOVERY_REQUIRED`。
- `packs/*.idx`、`meta/meta-pack-*.jsonl`、`meta/{export_job_id}/{object_id}.json` 都必须进入 `recovery_index.json.files[]`，并记录文件路径、文件大小和 SHA256。恢复重建 manifest 前必须先校验这些文件。

## 6. v2 Manifest 模型

### 6.1 顶层字段

```json
{
  "manifest_version": "2.0.0",
  "disk_id": "...",
  "export_job_id": "...",
  "edge_code": "...",
  "seal_id": "...",
  "data_key_id": "...",
  "created_at": "...",
  "objects": []
}
```

### 6.2 对象公共字段

每个对象保留业务和校验公共字段：

```json
{
  "object_id": "...",
  "storage_mode": "PACK",
  "bucket": "...",
  "key": "...",
  "size_bytes": 123,
  "etag": "...",
  "last_modified": "...",
  "content_type": "...",
  "metadata": {},
  "plaintext_sha256": "...",
  "frame_total": 0,
  "estimated_landing_bytes": 8192,
  "object_status": "EXPORTED"
}
```

对象公共层删除以下旧字段：

- `relative_data_path`
- `nonce`
- `tag`
- `aad`
- `encrypted`
- `encryption_alg`
- `ciphertext_sha256`
- `ciphertext_size_bytes`
- `chunk_sha256`

`frame_total = 0` 表示 `PACK` 对象。`frame_total > 0` 表示 `FRAMES` 对象的总 frame 数。

加密算法不在每个对象上重复声明，统一由 `disk_info.json.security.encryption_alg = "AES-256-GCM"` 表达。每个解密数据单元在 `pack_ref`、`frames[]` 中记录自己的 `nonce/tag/aad`。

### 6.3 PACK 对象字段

`PACK` 对象必须包含 `pack_ref`：

```json
{
  "storage_mode": "PACK",
  "pack_ref": {
    "pack_path": "packs/pack-000001.dat",
    "pack_offset_bytes": 0,
    "ciphertext_size_bytes": 1040,
    "nonce": "...",
    "tag": "...",
    "aad": "...",
    "ciphertext_sha256": "..."
  }
}
```

约束：

- 一个对象在 pack 中只有一个密文片段。
- 每个对象片段独立生成 `nonce/tag/aad/ciphertext_sha256`。
- 同一个 `data_key_id + nonce` 必须全盘唯一。
- `ciphertext_size_bytes` 只表示密文字节数，不包含 GCM `tag`。当前 AES-GCM 下密文字节数等于明文字节数，`tag` 单独保存。
- pack 文件写入期间必须先写 `pack-*.dat.partial` 和 `pack-*.idx.partial`，pack 关闭并 `fsync` 后再原子重命名为正式文件。
- manifest 只能引用已经关闭并原子重命名完成的 pack 文件。
- pack 文件整体丢失时，该 pack 内对象全部标记为导入失败。
- pack 文件局部损坏时，Center 逐对象校验 `ciphertext_sha256` 和 AES-GCM tag；校验失败的对象拒绝导入，校验通过的对象继续导入。

### 6.4 FRAMES 对象字段

`FRAMES` 对象必须包含 `frames[]`：

```json
{
  "storage_mode": "FRAMES",
  "frames": [
    {
      "frame_index": 0,
      "frame_total": 2,
      "relative_frame_path": "data/{export_job_id}/{object_id}/000000.frame",
      "frame_offset_bytes": 0,
      "plaintext_size_bytes": 67108864,
      "ciphertext_size_bytes": 67108864,
      "nonce": "...",
      "tag": "...",
      "aad": "...",
      "ciphertext_sha256": "..."
    }
  ]
}
```

约束：

- `frame_index` 从 0 连续递增。
- `frame_total` 必须等于对象公共字段中的 `frame_total`。
- `frame_offset_bytes` 必须连续。
- 所有 `plaintext_size_bytes` 之和必须等于对象 `size_bytes`。
- 每个 frame 独立生成 `nonce/tag/aad/ciphertext_sha256`。
- 对象级 `plaintext_sha256` 在所有 frame 解密后计算并校验。
- `ciphertext_size_bytes` 不包含 GCM `tag`。读取密文时按该长度读取，再使用独立 `tag` 字段完成认证解密。

## 7. AAD 设计

Edge 和 Center 必须共用 Common 中的 AAD 构造函数，禁止两端各自拼字符串。

新增 `pack_object_aad(PackObjectAad)`：

```text
disk_id
seal_id
export_job_id
edge_code
bucket
object_key
size_bytes
etag
last_modified
pack_path
pack_offset_bytes
ciphertext_size_bytes
```

新增 `frame_object_aad(FrameObjectAad)`：

```text
disk_id
seal_id
export_job_id
edge_code
bucket
object_key
size_bytes
etag
last_modified
frame_index
frame_total
frame_offset_bytes
plaintext_size_bytes
ciphertext_size_bytes
relative_frame_path
```

要求：

- AAD 使用 Common `canonical_json` 序列化：对象字段按 key 字典序排序，不输出多余空白，字符串转义由 `serde_json` 负责。
- Edge 写 manifest 时记录 AAD bytes 的 base64 值。
- Center 导入时重新计算 AAD bytes，base64 后与 manifest 记录值一致，再使用原始 AAD bytes 解密。
- Common 增加 golden vector 测试，覆盖 PACK 和 FRAMES 两类 AAD。

- `export_object_frame.status` 使用 `PENDING/ASSIGNED/COPYING/EXPORTED/FAILED/SKIPPED`，用于跨盘 frame 独立分配、写盘和恢复。
- FRAMES 对象的 `export_object.status` 只有在所有 frame 均为 `EXPORTED` 后才能写为 `EXPORTED`。

- `unique(data_key_id, nonce)`
- `object_ledger` 对 `PACK` 对象增加 `unique(data_key_id, pack_nonce)`，其中 `pack_nonce` 不为空时生效。
- `object_frame_import.status` 使用 `REGISTERED/VERIFIED/MERGED/FAILED`。
- `VERIFIED` 表示该 frame 已完成密文 SHA256 校验、AAD 校验、AES-GCM 解密和明文 frame 暂存。
- `MERGED` 表示该 frame 已参与对象级合并上传并写入 `object_ledger`。

`chunk_import_part` 只用于跨盘 chunk 导入场景，不复用为 v2 frame 级对象导入表。

### 8.3 Nonce 全局账本

分表唯一索引不能保证 `PACK`、`FRAMES` 和跨盘 chunk 之间的全局 nonce 不重复。v2 新增双端 nonce 账本。

Edge 新增 `export_nonce_ledger`：

```text
id
export_job_id
disk_id
seal_id
data_key_id
nonce
storage_mode
object_id
frame_index
created_at
```

Center 新增 `import_nonce_ledger`：

```text
id
import_job_id
disk_id
seal_id
export_job_id
data_key_id
nonce
storage_mode
object_id
source_bucket
source_key
frame_index
created_at
```

约束：

- `export_nonce_ledger` 必须有 `unique(data_key_id, nonce)`。
- `import_nonce_ledger` 必须有 `unique(data_key_id, nonce)`。
- Edge 在加密前先登记 nonce；登记冲突时丢弃该 nonce 并重新生成。
- Center 在解密前先登记 nonce。
- Center 登记 nonce 发生冲突时，必须读取已存在账本记录。
- 已存在账本记录的 `disk_id/seal_id/export_job_id/object_id/frame_index/source_bucket/source_key/storage_mode` 与当前导入对象完全一致时，判定为同一封盘批次幂等重放，继续执行对象账本幂等检查。
- 已存在账本记录与当前导入对象不完全一致时，拒绝整个 manifest，错误码固定为 `NONCE_REUSED`。
- `PACK` 对象的 `frame_index` 固定为 `NULL`。
- `FRAMES` 对象的 `frame_index` 写入实际 frame 序号。
- 跨盘 chunk 复用该账本登记 nonce，不再依赖 `chunk_import_part` 与 `object_ledger` 之间的跨表人工检查。

## 9. 元数据冗余与恢复

新增 `manifests/recovery_index.json`：

```json
{
  "version": "2.0.0",
  "disk_id": "...",
  "data_key_id": "...",
  "edge_code": "...",
  "export_job_id": "...",
  "seal_id": "...",
  "manifest_path": "manifests/export_manifest.json",
  "manifest_sha256": "...",
  "manifest_bak_path": "manifests/export_manifest.bak.json",
  "manifest_bak_sha256": "...",
  "object_count": 100,
  "total_bytes": 123456,
  "pack_count": 2,
  "frame_count": 9,
  "files": [
    {
      "path": "packs/pack-000001.idx",
      "size_bytes": 1234,
      "sha256": "..."
    },
    {
      "path": "meta/meta-pack-000001.jsonl",
      "size_bytes": 1234,
      "sha256": "..."
    }
  ],
  "created_at": "...",
  "index_hmac_alg": "HMAC-SHA256",
  "index_hmac": "..."
}
```

`index_hmac` 使用 `disk_data_key` 对 canonical recovery index 内容计算，不包含 `index_hmac` 字段本身。

manifest hash 规则：

- `export_manifest.sha256` 计算对象是最终 `export_manifest.json` 文件字节。
- `export_manifest.bak.sha256` 计算对象是最终 `export_manifest.bak.json` 文件字节。
- `recovery_index.json.manifest_sha256` 必须与 `export_manifest.sha256` 内容一致。
- `recovery_index.json.manifest_bak_sha256` 必须与 `export_manifest.bak.sha256` 内容一致。
- `recovery_index.json.files[]` 中记录的每个文件必须在恢复前完成 SHA256 校验。
- Edge 写入 manifest 后再生成 recovery index，避免 recovery index 中记录的 hash 与实际文件字节不一致。

恢复顺序：

1. 读取 `disk_info.json`。
2. `disk_info.json` 读取失败时，读取 `disk_info.bak.json`。
3. 对成功读取的 `disk_info` 校验 `center_signature`。
4. 读取 `recovery_index.json`，提取 `edge_code/export_job_id/seal_id`。
5. 校验 `disk_info.edge`、`recovery_index.json` 中的 `edge_code/export_job_id/seal_id` 完全一致。
6. 根据 `edge_code + disk_id + data_key_id + export_job_id + seal_id + edge_auth_secret` 调用 Common KDF 派生 `disk_data_key`。
7. 验证 `recovery_index.json` 的 HMAC。
8. 校验 `recovery_index.json.files[]` 中记录的文件 SHA256。
9. 读取并校验 `export_manifest.json`。
10. 主 manifest 损坏时，读取并校验 `export_manifest.bak.json`。
11. manifest 主备均损坏时，根据已通过 SHA256 校验的 `packs/*.idx`、`meta/*.jsonl`、`meta/{export_job_id}/{object_id}.json` 重建候选 manifest。
12. 重建结果必须生成 `recovery_report.json`。
13. Center 操作员必须通过恢复确认接口把 `recovery_report.approved` 写为 `true`，系统才能进入导入流程。重新封盘必须在导入成功后按中控重新初始化流程执行。

`disk_info.json` 已损坏且不能被原子覆盖时，系统不得依赖盘内 `disk_status_code` 表达恢复态。Center/Edge 必须在本地数据库记录 `disk_runtime.status = CHECKING`、`disk_runtime.last_error_code = RECOVERY_REQUIRED`。盘内写入成功时，系统必须写入 `recovery_report.json`。系统成功恢复出已验证的 `disk_info.json` 后，才能继续使用盘内生命周期状态。

恢复检查未完成的盘必须进入恢复态。恢复态下禁止继续导出、导入、清理和重新初始化。

## 10. HTTP / WebSocket v2 通讯契约

本次整改属于开发期破坏性升级，HTTP 和 WebSocket 类型按 v2 直接替换。不保留 v1 DTO，不保留 v1 字段适配，不保留 v1/v2 双解析，不新增兼容转换器。

### 10.1 删除旧通讯字段

后端 API、WebSocket payload、前端 TypeScript 类型中删除以下 v1 对象字段：

- `relative_data_path`
- `nonce`
- `tag`
- `aad`
- `encrypted`
- `encryption_alg`
- `ciphertext_sha256`
- `ciphertext_size_bytes`
- `chunked`
- `chunk_group_id`
- `chunk_index`
- `chunk_total`
- `chunk_offset_bytes`
- `chunk_size_bytes`
- `chunk_sha256`

这些字段只允许出现在已删除代码、迁移前历史说明和测试删除记录中。v2 主流程代码不得继续序列化这些字段。

### 10.2 v2 API 对象字段

导出对象、导入对象和对象详情 API 统一使用 v2 对象摘要：

```json
{
  "object_id": "...",
  "storage_mode": "PACK",
  "bucket": "...",
  "key": "...",
  "size_bytes": 123,
  "estimated_landing_bytes": 8192,
  "etag": "...",
  "last_modified": "...",
  "plaintext_sha256": "...",
  "frame_total": 0,
  "object_status": "EXPORTED",
  "error_code": "",
  "error_message": ""
}
```

`PACK`、`FRAMES` 的 `nonce/tag/aad/ciphertext_sha256/pack_path/relative_frame_path` 默认不通过前端 API 暴露。调试接口也不得返回 `nonce/tag/aad`。
`frame_total = 0` 固定表示 `PACK` 对象。`frame_total > 0` 固定表示 `FRAMES` 对象的总 frame 数。

当前对象进度 API 和 WebSocket `current_object` 使用以下 v2 字段：

```json
{
  "object_id": "...",
  "storage_mode": "FRAMES",
  "bucket": "...",
  "key": "...",
  "display_name": "...",
  "size_bytes": 123,
  "done_bytes": 0,
  "remaining_bytes": 123,
  "speed_bytes_per_sec": 0,
  "frame_index": 0,
  "frame_total": 2,
  "object_status": "COPYING"
}
```

`current_object` 删除 `relative_data_path`。前端对象名称继续使用 `display_name`，对象完整路径继续使用 `key`。

中控同步记录 API 使用以下 v2 字段替换旧 chunk 展示字段：

```json
{
  "ledger_id": 1,
  "object_id": "...",
  "edge_code": "...",
  "source_bucket": "...",
  "source_key": "...",
  "source_size_bytes": 123,
  "plaintext_sha256": "...",
  "storage_mode": "FRAMES",
  "frame_total": 2,
  "import_bucket": "...",
  "import_key": "...",
  "export_job_id": "...",
  "import_job_id": "...",
  "imported_at": "..."
}
```

中控同步记录页面删除 `chunk_group_id`、`ciphertext_sha256` 展示。对象类型展示改为 `storage_mode = PACK`、`storage_mode = FRAMES`。

### 10.3 v2 容量字段

Edge 磁盘列表、Center 磁盘列表、导出任务启动结果、导入任务启动结果、WebSocket 盘级进度必须保留并使用以下容量字段：

- `capacity_bytes`
- `free_bytes`
- `reserve_bytes`
- `object_budget_bytes`

新增字段：

- `estimated_landing_bytes`

字段语义：

- `total_bytes/done_bytes/remaining_bytes` 继续表示源对象明文字节数。
- `estimated_landing_bytes` 只表示后端容量预算，不作为用户传输量展示。
- 前端主视图不得用 `estimated_landing_bytes` 替代 `total_bytes/done_bytes/remaining_bytes`。
- Center 当前磁盘进度类型必须新增 `free_bytes/reserve_bytes/object_budget_bytes`，不得继续只依赖 `capacity_bytes/total_bytes` 推导可用空间展示。
- Edge 当前磁盘进度类型必须把 `object_budget_bytes` 改为必填字段，不得继续用 `total_bytes/capacity_bytes` 作为兜底计算。

### 10.4 v2 状态字段

状态字段语义保持边界，不是为了兼容旧代码，而是为了保持状态权威清晰：

- `disk_status_code`：盘内生命周期状态，只能来自 `disk_info.json.status.code`。
- `runtime_status`：本端运行态，只能来自 `disk_runtime.status`。
- `export_job_status`：导出任务状态。
- `import_job_status`：导入任务状态。
- `object_status`：对象状态。
- `last_error_code/error_code`：错误原因。

禁止事项：

- 禁止输出 `disk_status_code = RECOVERY_REQUIRED`。
- 禁止输出 `runtime_status = RECOVERY_REQUIRED`。
- 恢复检查开始时输出 `runtime_status = CHECKING`、`last_error_code = RECOVERY_REQUIRED`。
- 恢复失败时输出 `runtime_status = ERROR` 和具体 `last_error_code`。

### 10.5 v2 WebSocket 事件

WebSocket 事件 payload 直接升级到 v2，不保留 v1 payload。Edge 和 Center 事件结构分开定义，前端不得用同一个任务字段同时表达导出和导入。

Dashboard 汇总事件统一使用 `global_progress` 字段。删除旧 `global` 别名，前端 WebSocket 合并逻辑不得再读取 `event.global`。

HTTP 分页响应统一使用：

```json
  "page": 1,
  "page_size": 20,
  "total": 0,
  "items": []
}
```

删除旧 `records`、`total_count` 响应别名，前端不得再用 `payload.records` 或 `payload.total_count` 兜底。

盘级事件必须包含：

```json
  "disk_id": "...",
  "disk_status_code": "INITIALIZED",
  "runtime_status": "COPYING",
  "capacity_bytes": 0,
  "free_bytes": 0,
  "reserve_bytes": 0,
  "object_budget_bytes": 0,
  "last_error_code": ""

```

Edge 导出任务事件必须包含：

```json
{
  "export_job_id": "...",
  "export_job_status": "COPYING",
  "total_bytes": 0,
  "done_bytes": 0,
  "remaining_bytes": 0,
  "object_total": 0,
  "object_done": 0,
```

Center 导入任务事件必须包含：

### 10.6 前端删除范围

前端同步删除：

- v1 manifest 类型。
- v1 object DTO。
- v1 chunk DTO。
- v1 object adapter。

前端直接使用 v2 TypeScript 类型。接口返回 v1 字段时视为后端错误，前端不做兼容渲染。

## 11. Edge 端实施方案

### 11.1 改造模块

- `crates/common/src/crypto/`：新增 PACK/FRAMES AAD 构造。
- `crates/common/src/manifest/`：替换为 v2 manifest 类型。
- `crates/edge-backend/src/disk_worker.rs`：删除整对象 `Vec` 加密写盘流程。
- `crates/edge-backend/src/export_runtime.rs`：导出进度改为按对象和 frame 聚合。
- Edge repository：写入 v2 `export_object` 和 `export_object_frame`。
- `sql/edge/`：调整迁移。

### 11.2 写盘流程

1. 扫描对象并创建导出任务。
2. 按对象大小确定存储模式：`size_bytes <= 64 MiB` 写入 `PACK`，`size_bytes > 64 MiB` 写入 `FRAMES`。
3. 为 PACK 对象计算 `pack_estimated_landing_bytes`，为 FRAMES 对象生成 frame 明细并计算每个 frame 的 `estimated_landing_bytes`。
4. 每块盘分配前重新读取 `free_bytes` 并计算 `object_budget_bytes`。
5. Edge Planner 在数据库事务内按 `estimated_landing_bytes` 分配 PACK 对象或 FRAMES frame。
6. `PACK` 对象追加写入当前 pack 文件。
7. `FRAMES` frame 按 `frame_size` 写入本盘 frame 文件。
8. `FRAMES` 密文单元先写入同目录 `.partial` 文件，完成后执行 `fsync`。
9. `PACK` 密文单元追加写入当前 `pack-*.dat.partial`，对应索引追加写入当前 `pack-*.idx.partial`。
10. `FRAMES` frame 完成后原子重命名为正式文件。
11. `PACK` 只在 pack 关闭时原子重命名 `.dat.partial` 和 `.idx.partial`，未关闭 pack 不得出现在 manifest 中。
12. 写入对象元数据和 pack index。
13. 更新 Edge 数据库对象状态、frame 状态。
14. 生成 `export_manifest.json.tmp`、`export_manifest.bak.json.tmp`、哈希文件和 `recovery_index.json.tmp`。
15. 全部 `fsync` 后原子重命名。
16. 封盘前扫描 `.partial`，存在残留则进入恢复检查，不允许封盘。

## 12. Center 端实施方案

### 12.1 改造模块

- `crates/common/src/manifest/`：使用 v2 manifest 类型。
- `crates/center-backend/src/import_worker.rs`：删除 v1 `relative_data_path` 单文件导入流程。
- `crates/center-backend/src/import_runtime.rs`：按对象和 frame 更新导入进度。
- Center repository：写入 `object_ledger` 和 `object_frame_import`。
- `ArchiveStorage`：新增 `upload_object_from_path`，Center 将解密后的对象写入本地导入临时文件后按文件路径上传，避免整对象进入内存。
- `sql/center/`：调整迁移。

### 12.2 导入流程

1. 读取 `disk_info.json`；读取失败时读取 `disk_info.bak.json`。
2. 校验 `disk_info` 的 `center_signature`，从已验签的 `disk_info.disk.disk_id` 和 `disk_info.security.data_key_id` 取得 `disk_id/data_key_id`。
3. 读取 `recovery_index.json`，提取 `edge_code/export_job_id/seal_id`。
4. 校验 `disk_info.edge`、`recovery_index.json` 中的 `edge_code/export_job_id/seal_id` 完全一致。
5. 根据 `edge_code + disk_id + data_key_id + export_job_id + seal_id + edge_auth_secret` 调用 Common KDF 派生 `disk_data_key`。
6. 校验 `recovery_index.json` 的 HMAC。
7. 校验 `recovery_index.json.files[]` 中记录的文件 SHA256。
8. 校验主 manifest hash，失败则使用备份 manifest。
9. 校验 manifest 与 recovery index 的 `disk_id/data_key_id/edge_code/export_job_id/seal_id/object_count/total_bytes/pack_count/frame_count` 完全一致。
10. 对每个对象按 `storage_mode` 分支导入。

`PACK` 导入：

1. 打开 `pack_path`。
2. seek 到 `pack_offset_bytes`。
3. 读取 `ciphertext_size_bytes`。
4. 校验 `ciphertext_sha256`。
5. 通过 Common 重算 PACK AAD。
6. AES-256-GCM 解密。
7. 校验 `plaintext_sha256`。
8. 上传到归档存储。
9. 写入 `object_ledger`，同时记录 `data_key_id/pack_nonce/pack_ciphertext_sha256`。

`FRAMES` 导入：

1. 按 `frame_index` 顺序打开 frame 文件。
2. 校验每个 frame 的 `ciphertext_sha256`。
3. 通过 Common 重算 FRAMES AAD。
4. AES-256-GCM 解密每个 frame。
5. 将解密后的明文 frame 写入 Center 本地 frame 暂存文件。
6. 写入 `object_frame_import`，状态为 `VERIFIED`，记录 `staged_plaintext_path` 和 `staged_plaintext_sha256`。
7. Center 查询 `object_frame_import`，按 `export_job_id + object_id` 汇总已导入 frame。
8. 已导入 frame 数量等于 `frame_total`，且 frame_index 从 0 到 `frame_total - 1` 连续时，按 frame_index 顺序合并为 Center 本地对象临时文件。
9. 合并过程中增量计算对象级 `plaintext_sha256`。
10. 对象级 `plaintext_sha256` 校验通过后，通过 `ArchiveStorage::upload_object_from_path` 上传本地对象临时文件。
11. 上传成功后写入 `object_ledger`。
12. 将该对象所有 `object_frame_import.status` 更新为 `MERGED`。

任何 hash、AAD、tag、对象级 sha256 校验失败，必须停止该对象导入并记录错误，不得写入成功账本。

Center 本地导入临时文件约束：

- frame 暂存文件和对象合并临时文件必须写入 Center 本地专用导入暂存目录。
- frame 暂存文件和对象合并临时文件权限必须限制为当前服务用户读写。
- 对象上传成功、写入 `object_ledger`、frame 状态更新为 `MERGED` 后，必须删除该对象全部 frame 暂存文件和对象合并临时文件。
- 导入失败时必须删除对象合并临时文件。
- frame 已完成 `VERIFIED` 但对象尚未凑齐全部 frame 时，frame 暂存文件必须保留，用于后续其他运输盘导入后的合并。
- frame 暂存文件删除失败或对象合并临时文件删除失败时，写入 `import_job.error_code = TEMP_FILE_CLEAN_FAILED` 并保留告警日志。
- 临时文件路径不得写入 manifest、运输盘、WebSocket 和前端响应。

10. 改 Center 导入：按 `PACK` 和 `FRAMES` 导入。
11. 改 `ArchiveStorage`：避免整对象进入内存。
12. 更新测试、fixture、开发日志和验收脚本。

## 14. 验收标准

- Edge 端不再生成旧 `.bin` 对象文件。
- Edge 端只生成 `manifest_version = 2.0.0` 的 manifest。
- Center 端只接受 `manifest_version = 2.0.0`。
- 主业务代码中不存在 v1 manifest 兼容导入分支。
- HTTP / WebSocket DTO 不包含 v1 `relative_data_path/chunk_*/nonce/tag/aad` 字段。
- 前端 TypeScript 类型不包含 v1 object DTO、chunk DTO 和 fallback parser。
- 小对象进入 `PACK`，较大对象进入 `FRAMES`。
- `data_key_id + nonce` 全盘唯一。
- Edge 通过 `export_nonce_ledger.unique(data_key_id, nonce)` 保证本次导出全盘 nonce 唯一。
- Center 通过 `import_nonce_ledger.unique(data_key_id, nonce)` 保证历史导入 nonce 唯一。
- `ciphertext_size_bytes` 语义统一为不包含 GCM tag。
- Edge 和 Center 使用同一个 Common AAD helper。
- Edge 和 Center 使用同一个 Common KDF helper。
- Center 能成功导入 Edge 生成的 PACK 对象。
- Center 能成功导入 Edge 生成的 FRAMES 对象。
- FRAMES 对象跨多块运输盘分配时，Center 必须在所有 frame 到齐后合并上传并写入 `object_ledger`。
- 任意 frame 密文被篡改时，Center 必须拒绝该对象导入。
- `disk_info.json` 损坏时，Center 必须通过 `disk_info.bak.json` 和 `recovery_index.json` 产出明确恢复结论，结论枚举限定为 `RECOVERABLE`、`UNRECOVERABLE`。
- manifest 主文件损坏时，Center 能使用备份 manifest。
- manifest 主备均损坏时，系统进入恢复检查，不自动导入。
- 导出和导入过程中不再把接近 10 GiB 的对象整体读入内存。
- Center 本地 frame 暂存文件和对象合并临时文件按状态清理，临时文件路径不出现在对外响应中。
- Edge 分配任务时必须按 `estimated_landing_bytes` 扣减容量，不得按 `size_bytes`、硬盘总容量分配。
- metadata、manifest、recovery index、pack index、日志、AES-GCM tag、nonce、AAD 和文件系统块对齐预算必须计入容量分配。
- 运输盘不保存明文 `disk_data_key`。
- 不修改 `docs/v1.0冻结/` 下任何文件。
