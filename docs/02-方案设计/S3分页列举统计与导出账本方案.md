# S3 分页列举单盘顺序导出方案

## 1. 背景

Edge 端通过 S3 API 读取本地 RustFS。标准 S3 `ListObjectsV2` 不能直接返回 bucket 总对象数、总大小或总页数，只能分页列举对象。

为降低实现复杂度，当前方案不做任务池、不做后台统计、不做多盘抢任务。先采用单盘顺序导出：

```text
插入一块运输盘
-> S3 从第一页开始分页列举
-> 已导出对象跳过
-> 未导出对象拷贝到当前盘
-> 拷贝成功后写 PostgreSQL 已导出账本
-> 当前盘空间不足时封盘
-> 下一块盘插入后重新从第一页列举，继续跳过已导出对象
```

本方案优先保证：

- 逻辑简单。
- 状态少。
- 好排查。
- 不需要多盘并发分配。
- 不需要维护待拷贝任务池。

## 2. 核心结论

本方案只保留一个关键账本：

```text
已导出对象账本
```

PostgreSQL 只记录已经成功写入运输盘并封盘可追溯的对象版本。

导出时不提前生成完整待拷贝任务表，也不预先统计 RustFS 全量对象总数。

因此前端不能一开始显示准确总对象数和总剩余大小，只显示当前导出过程中的运行统计：

```text
已检查对象数
已跳过对象数
已拷贝对象数
已拷贝大小
当前对象
当前页列举状态
当前盘剩余空间
```

## 3. S3 分页能力边界

`ListObjectsV2` 请求常用参数：

```text
bucket
prefix
max_keys
continuation_token
```

`ListObjectsV2` 返回常用字段：

```text
Contents[].Key
Contents[].Size
Contents[].ETag
Contents[].LastModified
KeyCount
IsTruncated
NextContinuationToken
```

关键限制：

- `max_keys` 表示每页最多返回多少个对象，不代表固定返回数量。
- 常见最大值是 `1000`。
- `KeyCount` 表示当前页实际返回对象数量。
- `IsTruncated=false` 才表示已经到最后一页。
- `NextContinuationToken` 只用于继续翻下一页，不用于去重。
- 标准 S3 不支持直接查询总对象数。
- 标准 S3 不支持直接查询总页数。
- 标准 S3 不支持按 `LastModified` 时间排序分页。
- 默认分页顺序通常按 object key 字典序。

## 4. 单盘导出流程

### 4.1 插盘识别

```text
识别运输盘
-> 检查文件系统必须是 ext4
-> 读取 disk_info.json
-> 确认盘内生命周期状态为 INITIALIZED
-> 当前盘进入 READY
```

### 4.2 创建导出任务

只为当前运输盘创建一个导出任务：

```text
创建 export_job
-> 绑定当前 disk_id
-> export_job_status = COPYING
```

这里不创建全局任务池，不等待其他运输盘。

### 4.3 S3 从第一页开始列举

```text
continuation_token = 空

循环：
  调用 ListObjectsV2
  处理当前页 Contents
  如果 IsTruncated=false：
    结束列举
  否则：
    continuation_token = NextContinuationToken
```

每次新盘开始导出时，都从第一页重新列举。

## 5. 去重和拷贝

对当前页每个对象按顺序处理。

对象版本身份建议使用：

```text
bucket
object_key
etag
size_bytes
```

可选审计字段：

```text
last_modified
```

判断规则：

```text
如果历史已封盘导出账本中存在同一个 bucket + object_key + etag + size_bytes
  -> 跳过

否则
  -> 检查当前盘空间
  -> 空间够则拷贝
  -> 拷贝成功后写 PostgreSQL 已导出账本
```

拷贝前需要再次确认对象仍然是同一版本：

```text
当前 S3 对象 etag + size_bytes 与列举时一致
```

如果对象已删除：

```text
记录 SOURCE_MISSING，跳过
```

如果对象版本变化：

```text
记录 SOURCE_CHANGED，跳过
```

## 6. 盘满处理

每个对象写入前检查当前盘可用空间。

如果当前盘剩余空间不足：

```text
停止继续拷贝
-> 对已成功写入的对象生成 manifest
-> 封盘
-> 标记 export_job_status = SEALED
-> 前端提示可拔盘
```

盘满时不删除已成功写入的数据。

剩余未导出的 RustFS 对象不需要记录成待拷贝任务。下一块运输盘插入后，从 S3 第一页重新列举，通过已导出账本跳过旧对象，继续拷贝未导出的对象。

## 7. 列举完成处理

如果 S3 已经列举到最后一页：

```text
IsTruncated=false
```

则根据当前盘是否有成功写入对象处理。

当前盘有数据：

```text
生成 manifest
-> 封盘
-> export_job_status = SEALED
```

当前盘没有数据：

```text
不封盘
-> 运输盘保持 INITIALIZED / READY
-> 前端提示没有新的待导出对象
```

## 8. PostgreSQL 账本

本方案不使用“待拷贝任务池”。

PostgreSQL 主要记录已经成功导出的对象版本。

建议记录：

```text
export_job_id
disk_id
bucket
object_key
etag
size_bytes
last_modified
copied_at
object_status
```

对象成功写入运输盘并完成校验后：

```text
object_status = EXPORTED
```

封盘成功后，对应导出任务：

```text
export_job_status = SEALED
```

下次去重只认：

```text
object_status = EXPORTED
且 export_job_status = SEALED
```

这样可以避免把未封盘成功的数据误认为已完成导出。

## 9. 前端展示

前端不展示准确总数和准确剩余量。

展示当前运行状态：

```text
正在列举 RustFS
已检查对象数
已跳过对象数
已拷贝对象数
已拷贝大小
当前对象
当前运输盘剩余空间
当前写入速度
```

文案建议：

```text
正在列举 RustFS：已检查 11,436 个对象
已跳过：10,800 个
已拷贝：636 个 / 320 GiB
当前对象：bucket/path/file.dat
```

盘满后：

```text
当前运输盘已写满并封盘，可拔出。
插入下一块运输盘后将继续从 RustFS 第一页列举，并自动跳过已导出对象。
```

全部列举完成且没有新对象：

```text
没有新的待导出对象。
```

## 10. RustFS 新增对象处理

导出期间 RustFS 可能新增对象。

本方案不保证新增对象一定进入当前盘。

规则：

```text
本次 S3 分页列举过程中遇到的未导出稳定对象，可以拷贝。
本次没有遇到的新增对象，下一块盘或下一次导出再处理。
```

这样可以避免为了追实时新增导致状态复杂。

## 11. 优点和弊端

优点：

- 实现最简单。
- 不需要任务池。
- 不需要多盘 worker 抢任务。
- 不需要后台统计。
- 数据库压力较小。
- 出问题容易排查。

弊端：

- 每插入一块新盘，都要从 S3 第一页重新列举。
- 不能多盘并行提速。
- 前端不能提前显示准确总数和准确剩余量。
- 对象很多且已导出比例很高时，会有较多跳过判断。

## 12. 推荐落地顺序

第一步：调整导出流程为单盘顺序处理。

```text
插盘
-> S3 从第一页列举
-> 已导出跳过
-> 未导出拷贝
-> 成功后记账
```

第二步：完善盘满封盘。

```text
空间不足
-> 停止当前盘
-> 生成 manifest
-> 封盘
```

第三步：完善前端展示。

```text
已检查
已跳过
已拷贝
当前对象
当前盘状态
```

第四步：再根据现场数据量评估是否升级为多盘任务池。

## 13. 不做事项

本方案不做：

- 不做后台 RustFS 总量统计。
- 不做待拷贝任务池。
- 不做多盘并行抢任务。
- 不依赖 S3 直接返回总数。
- 不依赖 S3 返回总页数。
- 不把 `NextContinuationToken` 当去重依据。
- 不按 `LastModified` 做标准 S3 分页排序。
- 不修改冻结基线文档。
